# re-tbms-mall

의류 쇼핑몰·SKU 재고 관리·의류 시안 프로그램을 위한 Next.js + Python/FastAPI 프로젝트입니다.

현재는 **샘플 의류 쇼핑 홈과 로컬 관리자 진열 편집**을 제공합니다. 카테고리별 상품, 시즌·기획전 묶음, 상품 상세 보기, /about 회사 소개를 구성했습니다. 상품·가격·이미지는 샘플이며 실제 판매하지 않습니다. 운영 상품 등록·회원·재고 업무·시안 편집·DB·결제는 아직 구현하지 않았습니다.

## 로컬 시작 (Windows / Docker 불필요)

선행 조건: Node.js 24.18 이상 24.x, npm 11.16 이상 11.x, Python 3.11 이상(검증 환경 3.11.9), PowerShell. 이 단계는 DB·캐시·큐가 필요하지 않습니다. 운영 DB를 임의로 SQLite로 대체하지 않습니다.

저장소 루트에서 최초 설치 또는 잠금 파일 변경 시:

```powershell
cd C:\projects\re-tbms-mall
powershell -ExecutionPolicy Bypass -File .\scripts\setup.ps1
```

Python 선택이 필요한 경우 `-Python 'C:\path\to\python.exe'`를 전달합니다. 시스템 실행 정책은 변경하지 않습니다. 이 명령의 Bypass는 해당 프로세스에만 적용됩니다. 설치에는 패키지 다운로드 네트워크 연결이 필요합니다.

서로 다른 터미널 두 개에서 실행합니다.

```powershell
# 터미널 1: FastAPI
powershell -ExecutionPolicy Bypass -File .\scripts\dev-api.ps1
```

```powershell
# 터미널 2: Next.js
powershell -ExecutionPolicy Bypass -File .\scripts\dev-web.ps1
```

- 웹: http://127.0.0.1:3100
- API 문서: http://127.0.0.1:8100/docs
- API 상태: http://127.0.0.1:8100/api/v1/health
- 종료: 각 터미널에서 Ctrl+C. 스크립트는 다른 프로세스를 종료하지 않습니다.
- 포트 3100/8100 사용 중이면 소유 프로그램을 확인한 뒤 직접 정리합니다. 자동 포트 변경은 하지 않습니다.

## 환경변수

setup은 `apps/web/.env.example`을 `.env.local`로, `services/api/.env.example`을 `.env`로 복사합니다. 이미 있는 파일은 덮어쓰지 않습니다. 실제 환경 파일은 Git에서 제외됩니다.

`NEXT_PUBLIC_API_BASE_URL`은 브라우저에서 보이는 API 주소이므로 비밀값을 넣지 않습니다. 기본값은 `http://127.0.0.1:8100`입니다. API의 `CORS_ORIGINS`는 쉼표로 구분한 허용 origin 목록이며 기본 웹 주소만 허용합니다. 변경 후 서버를 재시작합니다. 기본 서버는 루프백 주소에서만 실행하며 외부 인터넷에 노출하지 않습니다.

## 상품 홈·회사 소개·진열 관리자

- 고객 홈: http://127.0.0.1:3100 — 상의·아우터·하의·원피스 샘플, 시즌 기획전. 개발 상태 정보 없음.
- 회사 소개: http://127.0.0.1:3100/about — 브랜드 소개용 임시 콘텐츠.
- 진열 관리: http://127.0.0.1:3100/admin/merchandising — 제목·설명·종류·상품 선택/순서·섹션 순서·공개 여부 설정.

관리 API는 로컬 전용 접근 키로 보호합니다. setup은 `.env`에 무작위 키를 만들고 기존 키는 보존합니다. 관리자 페이지에서 키를 입력하려면 본인 터미널에서 다음 명령으로 확인하세요. 키를 메시지·스크린샷·Git에 공유하지 않습니다.

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\admin-key.ps1 -Show
```

키를 새로 만들거나 변경하면 API를 재시작합니다. 로그인에 사용한 키는 서버 세션에 보관하고 브라우저에는 HttpOnly 세션 쿠키만 전달합니다. 로그인 상태는 새로고침 후에도 최대 8시간 유지되며 로그아웃 또는 웹 서버 재시작 시 만료됩니다. 이는 로컬 개발용 보호 장치이며 운영 회원 로그인·역할 권한 시스템이 아닙니다. 외부에 공개 배포하지 않습니다.

편집 결과는 `.local/storefront.json`에 저장되어 API 재시작 후 유지됩니다. 파일은 Git 제외이며 운영 DB 선택과 무관합니다. 단일 API 프로세스만 지원합니다. 다른 편집이 먼저 저장되면 충돌로 거절하므로 최신 내용을 다시 불러온 뒤 적용합니다. 파일 손상 시 기본값으로 덮어쓰지 않고 오류를 반환하므로 백업한 정상 파일로 복구합니다. 기본 분류·상품 자체는 샘플 fixture이며 이번 관리 화면은 진열 섹션을 편집합니다.

검증·제한: [상품 홈·진열 관리 검증 기록](docs/reviews/category-storefront.md).
## 공동 작업 보드와 다음 작업

http://127.0.0.1:3100/admin/workboard 에서 완료·진행·다음 제안·결정 필요 항목을 확인합니다. 진열 관리 화면에도 이동 링크가 있습니다. 원본은 루트 [workboard.md](workboard.md)이며 이 대화에서 요청한 변경을 구현·검증 결과와 함께 갱신합니다. 현재는 읽기 전용 보드이며 브라우저에서 편집하거나 에이전트 실행을 자동 추적하지 않습니다. 작업 보드와 원문도 관리자 로그인 후에만 볼 수 있습니다. 운영 배포 전에는 다중 계정·역할·지속 세션 등 별도 인증 설계가 필요합니다.

다음 우선 제안은 상품·SKU·재고 저장 기반 설계입니다. 운영용 관리자 인증과 DB 선택, 시안 프로그램 범위, 판매·결제 도입은 보드의 결정 필요 항목으로 관리합니다.

상품 진열은 화면보다 많을 때 5초 간격 자동 슬라이드와 이전/다음·정지 기능을 제공합니다. 사용자가 조작하는 동안과 동작 줄이기 설정에서는 자동 이동을 제한합니다. 하단 회사 정보는 실제 값 입력 전 등록 예정이며 정책 4종은 정식 정책이 아닌 준비 안내입니다.

문서 관리 형식과 작업 절차는 [작업 보드 안내](docs/workboard.md)를 따릅니다. 보드 화면에서 Markdown 원문을 펼쳐 보거나 [원문 URL](http://127.0.0.1:3100/admin/workboard/source)을 열 수 있습니다. 파일을 저장한 뒤 새로고침하면 반영됩니다.

## 관리자 시작 화면

- 관리자 홈: http://127.0.0.1:3100/admin
- 로그인: http://127.0.0.1:3100/admin/login

미로그인 상태에서 관리자 홈이나 하위 메뉴에 들어가면 로그인 화면으로 이동합니다. 로컬 개발에서는 **테스트 계정으로 바로 로그인** 버튼으로 진입할 수 있습니다. 서버에 설정된 기존 관리자 키로 API 연결을 확인하므로 웹과 API를 모두 실행해야 합니다. 기존 키를 직접 입력해 로그인할 수도 있습니다.

홈에서 상품·재고 관리, 진열 관리와 작업 보드로 이동합니다. 미구현 시안 등은 준비 중으로 구분합니다. 공통 관리자 메뉴에서 홈으로 돌아가거나 로그아웃할 수 있습니다. 테스트 바로 로그인은 개발 환경의 루프백 주소에서만 동작하고 운영 빌드에서는 버튼과 서버 기능이 비활성화됩니다. 현재 세션은 웹 서버 메모리에 저장하는 단일 프로세스 로컬 기능입니다.

## 관리자 업무 대시보드

관리자 홈에는 처리할 업무, 접수 Q&A, 의류 입고(예정/검수/완료), 배송 상태, 재고 부족을 요약과 목록으로 표시합니다. 현재는 기준 시각이 고정된 합성 샘플 데이터입니다. 실제 문의 접수·입고 기록·배송 연동·재고 원장으로 연결하는 작업은 후속이며, 이 화면에서 실업무를 완료 처리하지 않습니다. 상태 필터로 목록을 확인하고 기존 진열 관리·작업 보드로 이동할 수 있습니다.

## 상품·재고 로컬 관리

관리자 홈의 **상품·재고 관리** 또는 /admin/catalog는 상품·색상/사이즈별 재고·변경 이력을 보는 목록 화면입니다. 상품 등록(/admin/catalog/new), 색상·사이즈 등록(/admin/catalog/options/new), 상품 수정(/admin/catalog/[id]/edit), 재고 변경(/admin/catalog/inventory)은 별도 화면에서 진행합니다. 목록에서 해당 버튼을 눌러 이동하고 완료 후 목록으로 돌아와 확인합니다. 옵션 관리 코드는 색상·사이즈 조합을 구분하는 고유 코드입니다. 새 옵션의 재고는 0이며 수량 변경에는 증감량과 사유가 필요합니다. 새 상품은 고객 홈에 자동 게시되지 않습니다. 대시보드의 기존 업무 예시는 아직 고정 샘플이며 등록 DB와의 지표 연결은 후속입니다.

저장 파일은 .local/catalog.sqlite3이며 Git에서 제외됩니다. API 재시작 후에도 유지됩니다. 로컬에서는 Python 기본 SQLite를 사용해 별도 DB 설치가 필요 없습니다. 운영 DB선택과 배포는 별도입니다. DB파일 삭제는 상품과 재고 원장 삭제이므로 초기화 수단으로 사용하지 마세요. 파일 백업은 API를 정상 종료한 상태에서 DB관련 파일을 함께 보관하거나 SQLite 온라인 백업을 사용합니다. 지원되지 않는 스키마 버전은 자동 덮어쓰기 없이 오류로 처리합니다.

재고 요청 실패 후 같은 화면에서 같은 내용으로 재시도하면 동일 요청 ID를 사용합니다. 페이지를 새로고침하거나 닫으면 보관 중인 요청 번호는 사라집니다. 저장 성공 여부가 불명확할 때 새로 입력하거나 수량을 바꾸어 새 요청으로 보내기 전에 이력을 확인하세요. 현재 행위자는 공용 local-admin이며 개인 계정별 감사는 후속입니다. 주문 예약·반품 격리·가격·배송 자동 처리는 아직 연결하지 않습니다.

## 상품명과 카테고리

상품 등록의 **고객 표시명**에는 고객에게 보여줄 이름을 입력하고, **카테고리**는 목록에서 선택합니다. **내부 관리명**은 저장 시 TOP-TEE-FA-000001 같은 형식으로 자동 생성됩니다. 순번은 세부 카테고리와 계절 조합별로 증가하고 동시 등록도 서로 다른 번호를 받습니다. 분류 또는 고객 표시명을 수정해도 발급된 내부 관리명은 유지됩니다. 내부명 접두사는 최초 등록 분류를 나타냅니다.

기본 카테고리는 시작용 상의·아우터·하의·원피스·기타이며 기존에 입력한 분류도 보존됩니다. 카테고리 자체를 관리하는 화면은 아래 세부 카테고리 단계에서 제공됩니다. 기존 상품명은 고객 표시명으로 유지하고 기존 상품에 내부 관리명을 부여합니다. 로컬 DB는 v1에서 v2로 이관되며 실제 DB의 변경 전 백업은 .local/catalog-before-v2-20261026-010319.sqlite3입니다. 복구 전에는 현재 DB도 백업하고 v2 이후 입력을 보존해야 합니다.

## 세부 카테고리와 계절

신규 상품은 대분류→세부 카테고리를 선택하고 봄·여름·가을·겨울 또는 사계절을 지정합니다. 내부 관리명은 TOP-TEE-FA-000001처럼 생성됩니다. 봄·가을은 SPFA이며 선택 순서와 무관합니다. 네 계절을 모두 선택하면 ALL로 통일하고 순번은 세부 분류와 계절 조합별로 증가합니다. 기존 상품의 관리명은 유지하며 세부 분류와 계절은 미지정 상태로 남습니다.

/admin/catalog/categories에서 카테고리 추가, 이름·표시 순서·사용 여부를 관리합니다. 코드와 부모는 생성 후 바꿀 수 없으며 삭제 대신 사용 중지합니다. 신규 등록에는 활성 대분류와 활성 세부분류가 필요합니다. 기존 상품의 분류/계절을 그대로 두고 표시명만 수정할 수 있습니다. 분류/계절을 바꾸더라도 이미 발급한 내부 관리명은 그대로입니다. 초기 분류 예시는 운영에 맞춰 관리할 수 있습니다. 시즌 기획전과 착용 계절은 별개입니다.

v3 이관 전 실제 로컬 DB 백업은 .local/catalog-before-v3-20261026-011717.sqlite3입니다. 이전 DB로 복구할 때에는 API를 중지하고 현재 DB와 새 입력분을 먼저 보존해야 합니다.


## 공장 협업 로컬 사용 순서

1. 내부 관리자에서 공장·공급처를 등록합니다.
2. 상품 상세 → 담당 공장·시안 공유 설정에서 공장 **한 곳**과 공유할 내부 시안을 선택합니다. 미선택 시안은 공장에 공개되지 않습니다.
3. `/admin/factories/accounts`에서 공장 계정을 발급합니다. 초기 비밀번호는 담당자에게 직접 전달하며 자동 발송하지 않습니다.
4. 상품 상세 또는 `/admin/factories/requests/new`에서 색상·사이즈별 추가 제작 수량을 요청합니다.
5. 공장은 `/factory/login`에서 로그인하여 배정된 상품·공유 시안·제작 요청만 확인하고 접수→제작 중→제작 완료로 처리합니다.
6. 실제 물품을 받은 뒤 내부 관리자가 재고 입고를 별도로 기록합니다. 제작 완료만으로 재고가 늘어나지 않습니다.

현재 내부 관리자 개인별 계정, 부분 제작·검수·요청별 부분 입고 연결, 운영 분산 인증은 후속 범위입니다.

상품 목록과 상세에서 담당 공장 및 시안·샘플 작업 상태를 확인할 수 있습니다. 내부 관리자와 담당 공장은 상태와 공유 메모를 기록하며 변경 이력이 남습니다. 추가 제작 요청의 제작 상태와는 별도이고 시안 완료로 재고가 바뀌지 않습니다.

시안·샘플 관리: 상품 상세에는 요약과 진입 링크만 표시합니다. `/admin/factories/progress`에서 목록을 보고, 상품별 관리 상세에서 이력을 확인한 뒤 별도 상태 변경 화면으로 이동합니다. 공장도 상품 상세→시안·샘플 관리→상태 변경 순서이며 저장하면 관리 상세로 돌아옵니다.
