# 결정 기록 v0.3

## 독립 작업 격리와 통합 후 정리 (WB80, 2026-10-27)

사용자가 현재 변경 보존과 별도 worktree 준비를 요청했다. 기존 HEAD/인덱스를 변경하지 않는 로컬 소스 스냅샷에서 관리형 worktree를 만들며 비밀·실행 데이터·캐시는 제외한다. 같은 폴더에서 파일 소유권만 나누는 대안보다 수정 격리를 우선한다. 이는 병합 충돌이 없다는 보장이 아니며 공통 계약과 런타임 자원은 별도로 분리한다. 추가 기능 통합 후 독립·통합 검증과 미통합 자료 보존을 확인하고 불필요 worktree 및 해당 작업 임시 파일을 정리한다. 게시/푸시/배포 승인은 포함하지 않는다. 상세 절차: development-process.md.

작성일: 2026-10-25. 이 파일은 합의 상태의 기준이다. 다른 문서는 이 파일과 충돌하지 않아야 한다.

## 개발 기반 구현 선택 (2026-10-25)

기술 담당의 가역적 구현 선택: Next.js App Router·TypeScript, npm과 package-lock, Python venv·pip와 고정 requirements, 루프백 웹 3100/API 8100, 독립 개발 터미널. 구체 설치 버전은 각 잠금 파일과 검증 기록을 따른다. 사용자 확정 사업 정책과 구분한다.

이번 단계는 stateless health 연결이며 DB·주문·결제·AI·시안 편집기는 추가하지 않는다. API 상태 경로는 /api/v1/health이며 기존 /v1 업무 API 경로 초안은 아직 구현되지 않았다.

## 상품 우선 홈과 관리자 진열 (2026-10-25)

사용자 확정: 메인은 카테고리별 상품 우선, 회사 소개는 /about, 고객 화면 개발 상태 제거. 카테고리 외 시즌·기획전 등 사용자 정의 상품 묶음을 관리자가 구성한다. 임시 분류·샘플 상품으로 시작한다.

이번 구현 선택: /admin/merchandising에서 섹션 이름·설명·종류·상품·순서·공개 여부 관리. 기본 분류와 상품은 12개 샘플 fixture이며 섹션 구성은 로컬 .local/storefront.json에 저장한다. 이것은 샘플 진열 설정 저장소로 운영 DB 선택을 의미하지 않는다. 로컬 접근 키로 관리 API를 보호하며 운영 회원·역할 인증을 구현했다고 간주하지 않는다. 단일 API 프로세스 개발 환경 전용이다.

## 진열 움직임·푸터·공동 작업 보드

사용자 요청: 상품이 많을 때 자동 슬라이드, 일반적인 회사 정보/메뉴/정책 푸터, 함께 보는 작업 보드.
기술 담당의 가역적 선택: 화면을 넘치는 섹션만 약 5초 간격으로 순환하고 수동 조작·일시정지 제공. 동작 줄이기 환경에서는 자동 시작하지 않는다. 회사 실정보는 미제공이므로 등록 예정으로 표시하며 정책 페이지는 검토 전 안내로 둔다.
작업 보드는 /admin/workboard에서 저장소 JSON을 읽는 공유 현황으로 시작한다. 채팅에서 합의한 변경을 문서와 함께 반영하며 브라우저 직접 편집·실시간 에이전트 추적 기능은 아니다. 결제/시안 범위/운영 DB 선택은 여전히 미정이다.

## Markdown 작업 보드 확정

사용자 요청에 따라 루트 workboard.md를 프로젝트 관리 원본으로 변경한다. 기존 /admin/workboard는 같은 Markdown을 읽어 표시하며 원문 확인도 제공한다. 기존 JSON 원본 방식은 폐기한다. 문서를 저장한 뒤 화면을 새로고침하여 확인하며 별도 동기화 작업은 없다. 웹 직접 편집이나 실시간 에이전트 추적은 이번 범위가 아니다.

## 로컬 상품·재고 저장 결정 (2026-10-26)

사용자의 다음 작업 진행 요청에 따라 WB06을 구현한다. 기술 담당의 가역적 선택은 Python 기본 sqlite3와 .local/catalog.sqlite3다. 별도 DB설치/Docker 없이 저장과 트랜잭션을 검증할 수 있고 추가 의존성이 없다. 운영 DB·ORM 선택은 별도이며 PostgreSQL 등으로 전환할 경우 명시적 마이그레이션이 필요하다.

초기 범위는 관리자 초안 상품/색상·사이즈 SKU와 수동 재고 증감이다. 실제 판매·게시·가격·주문예약·격리·배송은 연결하지 않는다. 새 SKU잔고는0이다. 사유와 서버 행위자 local-admin을 원장에 남기며 개인 계정별 감사로 간주하지 않는다. 기존 고객 샘플과 대시보드 고정샘플을 등록 DB와 혼합하지 않는다.

## 상품 관리 화면 용어·분리 (2026-10-26)

사용자 확정: 초안 등록을 상품 등록, SKU 등록을 색상·사이즈 등록으로 표시하고 등록과 목록 화면을 나눈다. 구현 선택: 목록 /admin/catalog, 상품 등록 /admin/catalog/new, 색상·사이즈 등록 /admin/catalog/options/new, 상품 수정 /admin/catalog/[id]/edit, 재고 변경 /admin/catalog/inventory. 내부 API의 SKU 용어와 미게시 상태는 그대로 유지한다.

사용자 요구: 내부 관리명/고객 표시명 구분, 카테고리와 등록 순서에 의한 내부명 자동 생성, 카테고리 콤보박스. 구현 선택: 카테고리 코드-카테고리별 6자리 이상 증가 순번을 서버 저장 트랜잭션에서 발급한다. 내부명은 생성 시 카테고리 기준이며 이후 분류/표시명 변경으로 바뀌지 않는다. 초기 상의·아우터·하의·원피스·기타 분류는 시작용이며 최종 운영 분류 확정은 아니다. 기존 자유 입력 분류는 보존 이관한다. 카테고리 관리 UI는 후속이다. 기존 name API 필드는 고객 표시명 의미를 유지하고 internal_name/category_id를 추가한다.

## 세부 분류·계절 코드 승인 (2026-10-26)

사용자 승인: 대분류/세부분류, 카테고리 추가·이름·순서·사용 여부 관리, 계절을 포함한 내부 관리명과 조합별 순번. ROOT-LEAF-SEASON-000001 형식으로 신규 발급하며 기존 관리명은 유지한다. 구현 선택: SP/SU/FA/WI 고정순서, 모두 선택은 ALL로 정규화. 초기 세부분류 예시는 관리자가 수정 가능하다. 코드와 부모는 생성 후 고정, 삭제 없이 사용 중지한다. 기존 root 상품/미지정 계절은 보존하고, 분류·계절 변경 시 유효한 활성 세부분류/계절을 요구한다. 시즌 기획전은 상품 분류/착용 계절과 별개다.

## 사용자 글자 크기 (2026-10-26)

사용자 요청: 작은 텍스트 개선과 사용자에 따른 확대 기능. 구현 선택: rem 기반 글자 토큰, 기본/크게/더 크게 3단계 및 브라우저 localStorage 저장. CSS zoom 대신 글자와 유연한 레이아웃을 사용해 고정 화면 확대를 피한다. 계정 저장은 인증 API/개인 설정 모델을 추가해야 하므로 이번에는 포함하지 않는다. 작은 안내문 기본 크기를12px에서14px로 높인다. 서버 기본 렌더 후 저장값 복원으로 초기 크기 변화가 있을 수 있다.

후속 사용자 지시(WB22): 상단에 설정을 항상 펼쳐두지 않고 톱니바퀴에서 별도로 설정한다. 구현 선택은 기존 헤더의 설정 버튼과 native dialog이며 브라우저 표시 설정 계약은 유지한다. 현재 설정 항목은 글자 크기만 제공한다.

후속 사용자 지시(WB23): 톱니바퀴는 사이트 설정 전체의 진입점이며 글자 크기는 여러 설정 중 하나다. 구현은 공통 사이트 설정 셸·화면 및 접근성 분류·글자 크기 항목을 분리한다. 향후 설정 후보와 저장/권한 범위는 docs/site-settings.md에 제안으로 기록하며 아직 승인/구현된 기능으로 표현하지 않는다.

사용자 요청은 상품 삭제와 목록 작업 UI 개선이다. 구현 선택: 연결SKU가 없는 상품의 확인 후 삭제만 제공한다. 옵션·재고 이력을 연쇄 삭제하지 않으며 재고0인 옵션도 연결로 보호한다. 대안인 보관/복원·옵션 일괄 삭제는 별도 상태 모델과 운영 정책이 필요하므로 이번 범위에 추가하지 않는다. 삭제 시 내부명 순번은 되돌리지 않으며 되돌리기 UI는 없다. 이는 연결상품 전체 삭제나 운영 데이터 삭제 승인이 아니다.

## 상품 준비 현황 (WB27)

사용자 요청은 완료 버튼 정렬과 등록 상품의 옵션/입고 준비 표시다. 구현 선택: 서버가 현재SKU와현재고에서4단계현황을 조회 시 산출한다. 모든 등록 옵션에 양수 재고가 있을 때 재고 준비됨이며 일부만 있으면 일부 옵션 재고 없음이다. 이 분류는 실제 판매 가능 여부나 게시 조건을 새로 확정하지 않는다. 게시·가격·실결제 등 기존 미정 기능은 유지한다. 준비 상태는 별도 저장하지 않아 재고 소진 시 다음 조회에 반영된다.

WB29: 게시상태를 별도 열로 표시한다. 현재 게시 연결이 없으므로 재고가 준비된 상품도 게시불가/게시기능준비중으로 안내한다. 옵션미등록·현재고없음은 준비미완료의 짧은사유로 함께 설명하며 상세에는게시미연결도항상명시한다. 일부 옵션 품절은 현황으로 설명하고 전체게시금지정책으로 새로확정하지않는다. 실제게시기능 도입시에는 서버게시계약으로 이 고정미연결안내를 교체해야한다.

## 색상·사이즈 기준정보 (WB30, 2026-10-26)

사용자 요청: 색상·사이즈 등 관리 도메인을 관리자가 등록하고 콤보박스에 바로 반영한다. 구현 선택: 색상/사이즈 각각 이름·코드·표시 순서·사용 여부를 관리하며 코드는 등록 후 고정한다. SKU 관리 코드는 독립 기준값이 아니라 상품 내부명-색상코드-사이즈코드 조합으로 서버에서 자동 생성한다. 재고는 이 SKU 단위를 유지한다. 초기 색상/사이즈를 임의로 확정해 넣지 않는다.

기존 SKU를 schema4 기준정보와 연결하되 코드·표시 이름·재고·버전·원장을 보존한다. 기준정보 이름 변경도 기존 SKU의 등록 시점 표시값을 바꾸지 않는다. 기존 옵션 연결과 감사 이력을 보호하기 위해 삭제 대신 사용 중지를 제공한다. 이 이름 보존 정책은 이번 구현 선택이며 기존 옵션 이름 일괄 변경 기능은 포함하지 않는다. 로컬 실행 방식과 고객 게시·실결제 미정 상태는 유지한다.

## 다중 옵션 일괄 등록 (WB31)

사용자 요청은 여러 색상·사이즈 조합을 한 번에 등록하고 등록 결과를 명확히 표시하는 것이다. 구현 선택은 색상×사이즈 전체 조합 미리보기와 기존 조합 제외, 신규 조합의 원자적 저장이다. UI 오작동과 과도한 요청을 제한하기 위해 각 선택 최대50개·전체200조합으로 제한한다. 기존 옵션의 재고/기준 수량/표시값은 갱신하지 않는다. 응답 유실 후 재시도는 기존 조합으로 반환하며 완료 화면은 신규/기존을 구분한다. 새 의존성·스키마 변경은 없고 실제 게시/판매 정책은 변하지 않는다.

## 조합별 초기 재고 (WB32)

사용자 요청: 모든 색상×사이즈가 판매 대상은 아니므로 일부 조합 제외 및 각 조합 재고 입력. 구현 선택: 신규 조합만 초기 입고0..1000000을 허용하고 양수는 '옵션 등록 시 초기 입고' 원장으로 남긴다. 기존 옵션의 수량 변경은 기존 재고 관리 화면을 사용한다. 서버는 조합 생성+입고를 원자 처리하며 재시도는 existing으로 분류해 이중 입고를 방지한다. 이는 판매/게시 허가나 운영 데이터 입력 승인이 아니다. 기존 batch API는 호환 유지하고 새 selected-batch 계약을 추가한다. 스키마·의존성 변경 없음.

## 조합별 재고 부족 기준 (WB34)

사용자 요청: 조합마다 다른 기준과 공통값 일괄 적용. 구현 선택: 신규 조합별 입력을 원본으로 하고 공통 도구는 버튼 클릭 시 현재 등록 대상에만 복사한다. 제외/기존 옵션은 바꾸지 않으며 이후 추가 조합은 기본0이다. 기존 옵션 수정 기능을 확장하지 않는다. 서버는 item값 우선, 누락 시 이전 공통값/0으로 호환한다. 새 UI는 각item값을 명시한다. 스키마·의존성 변경 없음.

## 재고 변경 완료 표시 (WB35)

사용자 요청은 재고 입고·조정 후 결과 인지와 공통 UX 규칙의 재발 방지다. 구현 선택: 재사용 SaveResult로 대상/전후/증감/사유/시각을 보여주고 새로 입력하기를 명시적 동작으로 분리한다. 전 재고는 현재 UI값 대신 확정 원장의 balance_after-delta로 산출해 동일 요청 재시도에도 맞춘다. 요청과 다른 원장 응답은 완료로 인정하지 않는다. 저장 후 목록 갱신 실패는 저장 실패와 분리하고 후속 조정은 조회 성공 전 막는다. 서버 업무 규칙/DB는 변경하지 않는다.

## 재고 목록·입력 분리 (WB36)

사용자의 기존 목록/등록 분리 요구를 재고에도 적용한다. /admin/catalog/inventory는 변경 이력 목록, /admin/catalog/inventory/new는 입력·완료다. 기존 입력용 링크는/new로 변경하고 완료/이력 확인은 목록으로 이동한다. API/DB 변경없음. 목록과 입력 화면 분리를 향후 작업·검증의 필수 항목으로 명시한다.

## 관리자 전체 화면 정리 (WB37)

사용자 요청에 따라 카테고리/색상·사이즈 기준정보/진열 목록과 입력을 분리하고 상품수정의 완료 표시를 개선한다. 대분류 등록은 기존 parent_id:null 서버 기능을 명시적 화면으로 노출하는 것으로 신규 분류 체계 정책을 만들지 않는다. 진열은 기존 전체문서 revision 계약을 유지하고 화면만 섹션별로 나눈다. 기본값/코드/권한/게시·판매 정책은 변경하지 않는다. 전체 화면 감사 결과와 예외는 검증 기록에 남긴다.

## 공통 초기 입고 (WB38)

사용자 요청에 따라 초기 입고 수량도 공통 적용한다. 구현 선택은 등록 대상 신규조합에 동일 수량 복사이며 기존 수량에 더하는 작업이 아니다. 제외·기존·선택밖조합과 부족 기준은 보존한다. 서버 selected-batch 계약을 그대로 사용하고 미저장 입력도구만 추가한다. 실제 재고 일괄 조정 기능으로 확대하지 않는다.

## 공통 도구 위치·도움말 (WB39)

사용자 요청대로 긴 설명은 물음표 도움말, 적용 도구는 대상 선택 아래에 배치한다. 검증 분리를 유지하기 위해 공통 입력에 별도 form 소유권을 명시한다. 도구 적용/실제저장 의미와 서버계약은 바뀌지 않는다.

## 재고 출고 분류 (WB40)

사용자 요청은 판매·지인 제공 등 출고 이유 관리다. 구현 선택은 판매/증정/불량폐기/기타의 초기 고정분류와입고/증감조정이다. 별도분류관리화면이나개인수령자정보를추가하지않는다. 판매기록은수동재고차감이며판매형태·주문·실결제·정산정책을확정하지않는다. 기존이력은미분류로보존하고 schema5의새컬럼만추가한다. 이관전온라인백업확보.

## 입고·출고 업무 흐름 (WB41)

사용자 요청: 상세사유선택입력,저장후이력목록이동,공장→보유재고와보유재고→고객구분. 이번구현은기존이동사유를입고/고객판매출고/기타/미분류로묶은관리보기다. 입고가실제로어느공장에서왔는지나출고고객/배송진행상태까지추론하지않는다. 거래처·발주·검수·배송연계는추후설계범위이며공장내원단/생산재고는기존프로젝트범위외다. 두흐름은동일SKU보유재고원장에연결되며재고를별도로중복집계하지않는다. reason선택입력만API완화,스키마변경없음.

## 재고 흐름별 작업 진입 (WB42)

사용자는 재고 흐름에 맞는 사용성 개선을 요청했다. 구현 선택은 기존 원장과 사유 코드를 그대로 사용하면서 작업별 바로가기와 입력 문구·허용 사유를 구분하는 것이다. 공장·공급처의 실제 신원, 발주, 배송 또는 고객 정보 모델은 추가하지 않는다. 새로운 의존성이나 DB 변경은 없다.

## 공급처와 재고 현황 (WB43)

사용자는 공장·공급처 등록 후 입고 시 선택 방식을 승인했다. WB42의 버튼·폼 구분만으로 요청한 현황을 충족하지 못한 점을 정정한다. 현재 재고와 입고·출고 내역을 별도 보기로 제공한다. 공급처명 snapshot은 과거 입고 증거를 보존하기 위한 구현 선택이다. 구클라이언트/초기 재고 호환 때문에 서버 supplier_id는 nullable이나 신규 수동 입고 화면에서는 필수로 선택한다. 실제 외부 발주·공장 생산·배송 연동을 확정하지 않는다.

## 다크 모드 (WB45)

사용자 요청에 따라 사이트 테마를 구현한다. 구현 기본값은 시스템 설정이며 라이트/다크 명시 선택은 해당 브라우저에 저장한다. 계정별·서버별 설정이 아니다. 상품 이미지에 반전 필터를 적용하지 않는다. 새 의존성·외부 서비스는 없다.

## 공급처 상세 정보 (WB46)

사용자가 명시한 영문명·대표자·전화번호와 함께 담당자, 이메일, 사업자등록번호, 주소, 메모를 추가한다. 공급처명 외 새 필드는 선택 입력이라는 구현 기준을 둔다. 국내 전화/사업자번호 형태를 강제하지 않고 사업자 인증·외부 주소 조회는 연동하지 않는다. 입고 원장에는 공급처 이름 snapshot만 유지하며 연락처 변경으로 원장을 재작성하지 않는다.

## 국가별 주소 (WB47)

사용자가 국내 검색/직접입력·해외 직접입력 및 기존주소 보존을 승인했다. 국가 미지정은 빈값으로 두고 주소로 국가를 추론하지 않는다. 기존 주소 필드를 재사용하고 country_code/region/city만 추가한다. 카카오 우편번호 검색(키 없이 사용하는 embed 방식)은 공식 가이드 확인 후 선택한 구현이며, 외부검색을 페이지접속만으로 로드하지 않는다. 기존값을 검색어로 자동전송하지 않는다. 이전 WB46의 외부주소검색 미연동 결정은 이번 사용자 요청 범위에서 변경한다.

## 관리자 폼 폭 (WB48)

사용자가 전체 등록·수정 폼의 너비와 간격 점검을 승인했다. 복합 폼은 본문폭(기존 최대1320px)을 활용하고 짧은 기준정보는 compact760px을 유지한다. 모바일<=767px 입력그룹은 1열이다. 본문폭 확대가 데이터 표의 열을 세로 카드로 바꾸거나 업무·저장계약을 바꾸는 것은 아니다. 신규 폼의 폭 유형을 목적에 따라 명시하고 예외 이유를 기록한다.

## 공급처 저장 및 전화 검증 (WB49)

사용자 지시로 WB46의 전화 형식 허용 범위를 강화하고 완료 화면을 목록 자동 이동으로 대체한다. 국내 숫자 최대11이며 해외 호환을 위해 선두 + 국제형식 최대15를 구현 기준으로 선택한다. 국제 길이 근거는 [ITU-T E.164](https://www.itu.int/rec/T-REC-E.164/en) Annex A이다. 국가별 실제 발급 규칙/개통 확인까지 구현하는 것은 아니다. 수정에서 바뀌지 않은 기존 연락처는 생략해 보존하고 변경 시 새 검증을 적용한다. 새 의존성·DB 이관 없음.

## 전화 입력 UX 수정 (WB50)

## 상품·재고 업무 분리 (WB53)

사용자는 메뉴와 화면 분리 및 상품목록 재고요약·보기 연결을 승인했다. 기존 /admin/catalog와 /admin/catalog/inventory 주소는 호환성을 위해 유지하고 메뉴 책임을 분리한다. 상품연결은 이름검색이 아니라 product_id이며 요약/기록을 동일하게 제한한다. 알수없는ID는 전체데이터로 대체하지 않는다. API/데이터모델은 기존 SKU관계를 재사용한다. 옵션조합등록의 초기입고는 기존동작을 유지하고 일상 재고변경은 재고관리에서 처리한다.

## 출고 업무 통합 (WB55)

사용자는 상단등록진입과 판매/기타출고 통합을 요청했다. 출고4사유는 기존 reason_code를 그대로 사용하고 입출고 원장 재분류/이관은 하지 않는다. 재고조정은 실출고와 구분한다. 과거 flow=customer/other 링크는 출고의 sale/gift 초기값으로 연결한다. 주문·배송 자동화를 확정하는 변경이 아니다.

## 상품 이미지 저장 (WB61)

사용자가 시안과 고객용 모델/의류 이미지의 분리를 요청했다. 초기 구현은 design/model/garment 세 종류의 관리자 이미지 자료로 분리하며 자동 고객 게시를 추가하지 않는다. 로컬 SQLite 이미지 테이블과 인증된 JSON data URL 전송을 구현 선택으로 사용한다. 외부 저장 서비스 지출과 운영 CDN은 확정하지 않는다. 기존 상품 테이블에 큰 이미지를 붙이는 대신 별도 조회로 카탈로그 목록 비용을 유지한다. Pillow를 검증·재인코딩에 추가해 파일 서명만 확인하는 대안보다 손상 검출과 메타데이터 제거를 강화한다. 운영 대용량 처리/저장소는 별도 결정한다.


## 공장 협업 (WB62)

사용자가 상품당 담당 공장 한 곳으로 명시 결정했다. 공장 계정은 내부 관리자가 발급하고 기존 공급처 ID에 연결한다. 내부 전체 관리자와 공장 포털의 세션·API를 분리하고 권한은 FastAPI에서 매번 검증한다. 공장 전체자료 자동공개 대신 상품별 명시 공유 시안만 제공한다. 제작요청 상태는 재고 입고와 별도이며 실제 수령 수량만 기존 입고 업무에서 반영한다. 진행중 요청이 있을 때 공장 변경 차단, 접수전 취소와 순차 진행은 초기 구현 기준이며 접수후 취소/부분입고 협상은 미정이다.


## 시안·샘플 진행 기록 (WB63)

사용자 예시의 상태 세 가지와 초기 작업대기를 별도 상품-공장 작업 상태로 구현한다. 추가 제작 요청의 접수/제작/완료와 혼합하지 않는다. 기록된 진행 상황은 최종 업무 승인이나 게시 자격이 아니다. 초기 구현은 내부 관리자와 배정 공장이 상태를 보고할 수 있고 보완 작업으로 이전 상태도 선택 가능하다. 별도 승인자/샘플검수/상태별 필수 첨부 규칙은 확정하지 않았다.


## 시안·샘플 업무 위치 (WB64)

사용자 피드백으로 WB63의 상품상세 인라인 변경폼·전체이력을 전용 공장협업 화면으로 이동한다. 상품 상세는 요약, 시안·샘플 상세는 조회·이력, 별도 변경은 입력으로 역할을 나눈다. 기존 상태/권한/버전/API/재고정책은 그대로 유지한다.

## 라운드 일관성 (WB65)

기존 폼의 12px을 버튼·패널의 공통 기준으로 확장한다. 임의 화면별 반경 대신 의미별 토큰을 사용하고 배지/원형 도움말만 형태 예외로 유지한다. 업무 규칙·API 변경은 없다.

## 상품 목록 행 작업 (WB66)

## 시안 상세 중심 관리 (WB67)

사용자 지시에 따라 상품 상세의 공장명은 상품별 시안 상세 진입점으로 사용한다. 버튼 중복을 제거하고 공장설정·추가제작요청은 시안 상세에서 접근한다. 미배정도 시안상세 진입을 허용해 설정 경로를 보존한다. 내부시안의 화면 위치만 변경하며 기존 레코드·API·공유권한을 변경하지 않는다.

## 상품 정보·이미지 드롭 (WB70)

전체화면 요청을 기존 관리자 routefamily의 시각적 위계 점검으로 해석한다. 신규 업무나 실제 데이터 연결을 추가하지 않는다. 이미 충분한 강조는 유지하고 숫자·상태·완료결과의 부족한 위계를 공통표현으로 보강한다. 비대화형 요약 KeyFacts와 기존 링크형요약을 구분해 탐색기능을 보존한다.

현재 상품목록의10열이 복잡하다는 피드백에 따라 동일대상 정보를 같은셀로 묶고6열로 축소한다. 상품설명만 목록에서 제거하고 상세에 유지한다. 별도 게시상태와사유도움말 요구는 유지하며 삭제/재고/상세/수정 접근을 없애지 않는다. 카테고리 표기만 >로 바꾸며 데이터변경없음.

새 인증 우회 엔드포인트 대신 기존 공장 아이디/비밀번호 로그인을 재사용한다. 서버가 ignored .local/factory-test-login.json에서 전용 합성 계정 자격증명을 읽고, 브라우저에는 세션 쿠키만 발급한다. ## 공장 대시보드 (WB84)

기존 공장 범위 workspace 응답으로 담당상품/시안/제작업무를 집계하며 관리자 샘플 대시보드 데이터를 재사용하지 않는다. 조회 요약은 클라이언트 표현이며 권한/상태전이 규칙은 기존 API에 유지한다. 홈의 반복 전체목록은 별도 상품/제작요청 목록으로 분리한다. 총계 카드는 목록으로, 개별 업무는 해당 상세로 연결한다. DB나재고 변경 없음.

## 샘플·완제품 물류 연결 — WB86

## 2026-10-30 WB118 반품·교환 방문 수거 방식 확정
사용자 확정: 판매자가 지정 택배사 방문 수거를 접수한다. 고객은 신청 시 회수 주소를 확인·수정하고 관리자가 접수 내용을 확인해 수거를 접수하는 흐름으로 설계한다. 지정 택배사·반품 주소는 미정이며 자동 택배 연동이나 외부 수거 요청 실행을 승인한 것으로 해석하지 않는다. 교환 상품 발송 시점은 다음 결정 항목이다. 정책 기록만 변경, 실제 관리자 화면/사용가이드/캡처 영향 없음.

## 2026-10-30 WB118 교환 상품 출고 기한 확정
사용자 확정: 기존 상품 회수·검수 및 필요한 고객 부담 배송비 결제 확인 후1~3영업일 이내 교환 상품을 출고한다. 배송비가 없는 판매자 귀책 교환은 별도 배송비 결제를 요구하지 않는다. 출고는 택배사 인계 기준이며 도착 보장일이 아니다. 교환 옵션 품절은 기존 결정대로 고객 안내 후 반품·환불로 전환한다. 배송비 결제 수단·PG 및 실제 교환 상태전이 구현은 후속 설계 항목이다. 정책 문서 변경만 수행하여 관리자 사용가이드·캡처 영향 없음.
