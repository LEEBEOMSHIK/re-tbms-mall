# WB141 / R111 주문 상태·데이터 설계안

2026-11-01 · 작성 root · 설계 제안, 구현/운영 적용 전.

## 목적과 현재 상태

PG 선정 전에 고객 주문 내역·관리자 주문/출고/클레임 화면과 서버 계약을 준비한다. 실제 결제·환불·예약은 연결하지 않는다. 기존 고객 DB의 `checkout_drafts`, `checkout_requests`는 작성 중인 주문서이며 구매 확정 기록이 아니다. WB134 입력은 같은 탭 sessionStorage에만 유지된다. 현재 `/orders` 역시 주문서 목록이다. 이미 판매 완료된 것처럼 이름만 바꾸지 않는다.

관련: `docs/contracts/customer-checkout.md`, `docs/contracts/customer-account.md`, `docs/decisions.md`의 WB118 정책, `docs/environments.md`. 담당 root, 후속 서버/화면 구현자는 본 문서의 계약을 먼저 확정한다. 이번 수정 파일은 본 문서·작업 보드·검증 기록뿐이며 API/DB 변경 없음. 관리자 가이드 영향 없음: 미구현 설계를 사용 절차로 추가하지 않는다.

## 확정 정책과 설계 선택

사용자 확정: 완제품 재고 판매, 로그인 고객 귀속, 주문당 배송지 한 곳·합배송, 판매자 사정 분할 배송 추가비 판매자 부담. 할인 후 상품금액 50,000원 이상 기본배송비 무료, 미만 3,000원. 결제 확인 후 1~3영업일 출고. 국내 배송만, 제주·도서산간 추가 운임 결정 전 결제 제한. 결제 시작 시 10분 확보·승인 시 판매 확정. 준비 전 직접 취소, 준비 이후 관리자 확인, 발송 후 반품 절차. 반품·교환 비용/기간은 결정 기록의 최신 확정 정책을 참조한다.

기술 대안:
- 하나의 status: 단순하지만 부분 발송·환불 처리 중·결제 결과 불명확을 표현하기 어렵다.
- **주문·결제·출고·클레임을 분리하고 고객용 상태를 계산(권장)**: 필요한 사실을 손실 없이 보존하며 UI는 핵심 상태만 보여준다.
- 전체 이벤트 소싱: 감사 추적은 강하지만 현재 단일 쇼핑몰 규모에서 복구·조회 복잡도가 크다. 상태 테이블+변경 이력+작업 큐로 시작한다.

위 권장안과 테이블·상태 이름은 구현자의 제안이다. 사용자가 새 사업 정책 또는 구현을 승인한 것으로 표현하지 않는다. 새 외부 서비스나 Docker·큐 제품은 도입하지 않는다.

## 상태와 전이

| 영역 | 상태 | 전이/권위 |
|---|---|---|
| 주문 | awaiting_payment → confirmed → closed; awaiting_payment → expired/cancelled | confirmed는 서버가 PG 승인과 유효 재고 확보를 함께 검증한 뒤에만. closed는 배송/클레임 정산 종결, 자동 구매확정 기간은 미정 |
| 결제 시도 | created → pending → succeeded / failed / cancelled; pending → unknown | unknown은 시간초과 등 결과 미확정. PG 조회로만 해소. 웹 성공 URL만으로 succeeded 금지 |
| 재고 확보 | held → allocated / released; held → reconciling | held는 결제 시작부터10분, allocated는 승인 후 출고 대기분. 결과 불명확 시 조회 전 확정/임의 해제 금지 |
| 출고 단위 | unprepared → preparing → shipped → delivered | 관리자가 준비·실제 인계 확인. 송장 등록만으로 shipped 금지. 배송완료 근거와 기록자 보존 |
| 취소/반품/교환 요청 | requested → reviewing → approved → processing → completed; rejected / withdrawn는 종료 | 종류별 허용 전이는 별도 검증. 취소의 직접 처리 가능 조건은 서버가 원자적으로 판단 |
| 환불 시도 | requested → pending → succeeded / failed / unknown | PG 성공 검증 후에만 환불 완료. 실패/unknown은 원래 주문·출고 상태를 덮어쓰지 않음 |

고객 표시 예: 결제 대기, 결제 확인 중, 결제 완료, 상품 준비 중, 일부 발송, 배송 중, 배송 완료. 환불/교환 진행은 별도 보조 상태로 표시한다. 한 상품의 반품 요청으로 주문 전체를 반품 완료로 표시하지 않는다. 배송완료와 구매확정/리뷰 자격은 동일시하지 않으며 후속 계약으로 분리한다.

## 데이터 경계와 제약(제안)

금액은 KRW 정수, 수량은 양의 정수, 시각은 UTC 서버 기준. 내부 UUID와 표시용 주문번호는 분리한다. 모든 쓰기에 고객/관리자 권한, version, request_id, payload hash를 적용한다.

| 테이블 | 주요 필드·제약 |
|---|---|
| sales_orders | id, public_number UNIQUE, customer_id, checkout_id, checkout_version, status, version, currency, goods_total, shipping_total, grand_total, policy_version, created_at/confirmed_at. 결제 시작 요청의 중복 방지키 UNIQUE |
| sales_order_lines | order_id, line_id, sku_id, 상품명/색상/사이즈 스냅샷, 주문수량, 정가/할인/확정단가/행금액. 수정된 상품명·가격이 기존 주문을 바꾸지 않음 |
| order_shipping | order_id UNIQUE, 받는 분·연락처·우편번호·주소·상세주소·메모 사본, 지역판정 자료 버전. 주소록 수정/삭제와 독립 |
| payment_attempts | order_id, attempt_id, provider, provider_payment_id UNIQUE(nullable), amount/currency, status, requested_at, verified_at, idempotency_key UNIQUE. 비밀키/카드정보 저장 금지 |
| stock_reservations | order_line_id, sku_id, quantity, status, expires_at, version. 활성 확보 중복 금지, 확보/출고/반품 조정은 재고 원장과 연결 |
| shipments / shipment_lines | order_id, carrier_code, tracking_number, status, dispatched_at/delivered_at, order_line_id/quantity. 주문 배송지 한 곳 유지, 여러 출고 단위로 판매자 분할발송 표현 |
| claims / claim_lines | order_id, type, reason, liable_party, status, customer_note, line_id/quantity, 교환대상sku, 회수/검수/안내 이력. 요청 중 수량과 완료 수량을 중복 소비하지 않음 |
| refunds / refund_allocations | claim_id, attempt_id, PG환불ID, 상품환급/최초배송비환급/차감운임/최종환급, status; 행별 금액·수량 배분 및 고유 재시도키 |
| order_events | order_id, actor_type/id, action, before/after 상태, request_id, timestamp. 개인정보 원문·PG 응답 전체는 기록 금지 |
| payment_inbox / order_outbox | 공급자 이벤트ID UNIQUE, 최소 정규화 내용/처리 상태; 재조회·환불·후속처리 작업키 UNIQUE, 시도횟수·다음시각·마지막 오류분류 |

계산 불변식: grand_total = 확정 할인 후 goods_total + 확정 shipping_total. 환불 누계는 승인된 수납액을 초과할 수 없다. 동일 주문행의 취소·발송·반품·교환 수량은 각 단계별 원수량 범위를 초과할 수 없다. 할인 배분과 운임 차감은 스냅샷 기준으로 계산하며 최초 배송비 중복 청구 금지. 일부 환불은 행별 배분 내역을 남겨 여러 요청의 누적 오차를 막는다.

## DB·재고 일관성

현재 고객 DB와 상품/재고 DB는 별개다. 두 연결을 한 트랜잭션인 것처럼 처리하지 않는다. 권장안은 주문·결제시도·예약·출고 원장 테이블을 재고 저장소와 같은 SQLite 트랜잭션 경계에 두는 것이다. 고객 인증/주소록/기존 초안은 고객 DB에 유지하고 customer_id는 서버 인증 결과로만 채운다. DB간 FK 대신 주문 생성 시 계정 검증, 이후 매 요청 소유권 검증을 수행한다.

초안의 상품 목록과 브라우저 최신 배송 입력을 결제 준비 요청으로 받되, 가격/고객ID/주문 상태는 받지 않는다. 서버가 초안 소유권·version을 확인한 뒤 재고 DB 트랜잭션에서 공개상태·가격·지역·가용수량을 다시 평가하고 불변 주문 사본을 만든다. 고객 DB에 변환 표시를 쓰는 것은 재시도 가능한 후속 작업이다. 실제 중복 방지는 주문 DB의 request_id 및 활성 초안 변환 제약이 담당한다. 동일 요청키+다른 본문은409, 동일본문은 같은 결과를 반환한다.

재고 제안: 가용수량 = 실보유수량 − 결제 확보수량(held 및 reconciling 모두 포함) − 승인 후 출고 배정수량. 승인 시 held→allocated, 실제 출고 시 보유수량 차감+allocated 해제는 한 트랜잭션. 준비 전 취소는 배정 해제, 반품은 검수 전 판매가능 재고에 가산하지 않는다. 기존 수동 출고/재고 조정도 예약·배정 수량을 침범하지 않게 공통 재고 서비스로 통합해야 한다. 이 변경은 API 검증을 포함하는 별도 구현이며 기존 재고 숫자의 의미를 조용히 변경하지 않는다.

## 결제 시작·만료·승인 경합

1. PG 및 배송지역 자료가 준비되지 않으면 현재503/비활성 동작 유지. 미확정 최종금액으로 결제 요청 생성 금지.
2. 결제 시작 시 변경된 금액/배송조건은 고객에게 재확인시킨다. 동일 조건 확인 후 SKU를 일정한 순서로 검증하고 원자적 확보·결제시도·작업 기록을 생성한다. PG 네트워크 호출 중 DB 잠금을 유지하지 않는다.
3. PG 응답/웹훅은 서버 조회로 금액·통화·주문·상점·거래ID를 확인한다. 서명 방식은 선정 PG 계약에 따른다. 중복/순서 뒤바뀜에도 같은 승인·재고처리는1회만.
4. 만료 처리와 승인 처리는 version/조건부 갱신으로 직렬화한다. 이미 해제된 확보에 늦은 승인이 오면 출고 확정 금지, 자동취소/환불 보상 작업으로 전환한다. 같은 SKU를 다른 주문에서 다시 확보한 것을 소급 사용하지 않는다.
5. 10분 시점에 PG 결과가 불명확하면 기존 확정 정책대로 PG 조회 후 해소한다. 재조회 간격·운영 경보·확인 중 확보의 최대 운영 처리시간은 PG 특성에 맞춰 결정할 미정 항목이다. 고객에게 임의로 결제 실패/예약 연장을 확정 표시하지 않는다. reconciling도 가용수량을 계속 차감한다. 조회 결과 유효 승인 확인 시 원자적으로 allocated, 확정 실패/취소/미결제 만료 확인 시 released로 전환한다. 여전히 결과가 불명확하면 reconciling 유지와 운영 경보만 수행하며 기한이 지난 held로 되돌리지 않는다.
6. 결제 응답 유실 후 새 시도를 무조건 생성하지 않는다. 기존 active attempt를 조회하여 중복 청구를 막는다. 주문이 미결제 상태이고 직전 시도가 failed/cancelled로 확인된 경우에만 새로운 키로 재시도한다. succeeded는 재시도 대상이 아니다. 주문당 활성 시도(created/pending/unknown)는 최대1개, 유효 승인도 최대1개라는 DB 제약과 조건부 상태 전이를 함께 적용한다. 만료/취소 주문은 기존 주문에 재결제하지 않고 새 주문 준비 흐름을 거친다.

## 취소·출고·클레임 경합

- 고객 직접 취소와 관리자 preparing 전환은 같은 주문/출고 version 조건으로 경쟁한다. 취소가 먼저면 준비 금지, 준비가 먼저면 관리자 확인 요청으로 접수한다.
- 취소 확정 의사가 등록된 주문은 출고 차단. PG 환불 결과 불명확 시 ‘취소 처리 중’으로 유지하고 환불 완료로 표시하지 않는다. 재고 배정 해제 시점과 환불 처리 상태는 별도 기록한다.
- 한 번에 여러 요청이 들어와도 취소/반품/교환 대상 행수량을 원자적으로 점유한다. 동일 배송 건 회수비를 개수별로 반복 부과하지 않는다.
- 발송 후 취소 요청은 반품 접수로 안내한다. 회수·검수, 책임 주체, 배송비 정산은 기록 후 처리한다. 교환 옵션 품절 시 고객 안내/동의 기록 후 반품·환불 흐름으로 전환한다.
- 교환 출고는 회수·검수와 필요한 운임 결제 확인 후에만 가능하다. 판매자 귀책으로 고객 부담0원인 경우 별도 결제를 기다리지 않는다.

## API·화면 계약 초안

신규 `/api/v1/customer/sales-orders`와 `/api/v1/admin/sales-orders`로 기존 checkouts와 구별한다. 상세 GET, 고객 cancel-requests/claims POST, 관리자 prepare/ship/claim-decision 명령별 POST를 제공한다. 범용 status PATCH는 제공하지 않는다. 목록은 cursor 페이지 처리, 고객 타계정404/미인증401, 관리자 권한없음403, 버전/상태충돌409, 입력422를 사용한다.

PG 연결 전 개발용 합성 주문은 별도 테스트 DB/fixture로만 제공한다. 운영 고객에 ‘결제 완료 만들기’나 수동 입금확인 버튼을 노출하지 않는다. 주문서 UI의 ‘결제 준비 중’과 입력 보존은 유지한다. 새 고객 주문내역은 `/account/orders` 제안, 기존 `/orders` 초안 링크를 유지하여 호환 경로를 제공한다.

관리 화면은 목록 `/admin/orders`, 상세 `/admin/orders/{id}`, 출고 입력 `/admin/orders/{id}/shipment/new` 등 별도 URL. 목록에 전체 입력폼을 붙이지 않는다. 저장 확정·불확실·실패입력보존·후속동작은 공통 SaveResult와 디자인 시스템 규칙을 따른다. 실제 UI 구현 시 가이드 원문·캡처·표식을 동시에 추가한다.

## 호환·복구·개인정보

추가 테이블 마이그레이션으로 시작, 기존 checkout/cart/address/catalog 테이블·자료 삭제 금지. 적용 전 DB별 일관된 백업과 버전·복구 점검이 필요하다. PG를 끈 상태로 마이그레이션/읽기검증 후 기능 플래그로 활성화한다. 롤백은 새 쓰기 차단 후 기존 UI로 복귀하며 발생한 결제 기록을 삭제해서 맞추지 않는다. 재고 서비스 변경은 원장 대조 후 역변경한다.
