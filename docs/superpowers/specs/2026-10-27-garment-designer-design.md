# 내부 의류 디자인 편집기 설계 — WB83

작성일: 2026-10-27. 요구 연결: R18~R21 / D05 / Q02.
문서 성격: 사용자 확정 범위와 구현자 제안을 구분한 설계안. 상세 설계 승인 및 구현 계획 작성 전이며 기능 구현 완료를 뜻하지 않는다. 작업 상태는 원본 workboard.md에서만 관리한다.

## 사용자 확정 범위

- 내부 관리자가 제작 전에 옷의 느낌을 확인하는 도구다. 고객/공장 편집 도구가 아니다.
- 초기 기본 의류는 티셔츠·후드다. 추후 실제 제작할 옷의 형태를 추가할 수 있어야 한다.
- 바탕색·원단 표면 질감·광택 및 나염 디자인 적용을 지원한다.
- 2D에서 편집하면 동일 디자인이 3D에 바로 반영되고, 3D는 회전·확대해 본다.
- 자수/패치 등 장식 방식, 주름/처짐, 3D 직접 편집의 확장 경계를 마련한다. 이 후속 기능을 지금 구현하는 것으로 해석하지 않는다.

## 목적과 제외 범위

선택한 의류에 색·원단 느낌·나염을 바꿔 적용하고 저장 후 다시 편집할 수 있는 내부 시안 도구를 만든다. 이미지만 등록하는 기존 공장 협업 시안 관리와 편집 가능한 디자인 문서를 구분한다.

실측 피팅·천 물리 시뮬레이션·생산 패턴·인쇄용 색분해/CMYK·실제 발색 보증·AI·결제·고객 공개는 이번 범위가 아니다. 생산 방식 확장을 위해 처음부터 범용 플러그인 실행기나 외부 코드 업로드를 만들지 않는다.

## 검토한 접근

1. 2D 편집 + 3D 동시 미리보기: 정밀 입력과 좌표 검증이 단순하며 동일 문서로 일치 검증 가능. 사용자가 선택했다.
2. 2D/3D 양쪽 직접 편집: 직관적인 표면 배치가 가능하지만 표면 선택·봉제선 경계·조작 충돌 복잡성이 높아 후속 확장으로 남긴다.

화면 프레임워크는 기존 Next.js/React, 서버는 FastAPI를 유지한다. 구현자 제안: 2D는 브라우저 Canvas 2D와 HTML 조작부, 3D는 Three.js를 client-only 모듈로 사용한다. 다른 React 렌더러 의존성을 추가하지 않는다. 정확한 Three.js/타입 버전은 구현 계획에서 기존 런타임 호환성을 확인하고 잠금 파일에 고정한다. 현재 문서는 설치/채택 완료 증거가 아니다.

## 초기 동작 — 구현자 제안

- 독립 디자인 목록 → 새 디자인(이름·티셔츠/후드 선택) → 편집 → 저장 결과 → 상세/목록 흐름.
- 바탕색은 의류 전체 한 색, 원단은 면 저지·폴리에스터·스웨트 원단의 시각 프리셋 3종과 광택 조절로 시작한다. 기모 내부 구조나 물성 계측값을 재현했다고 표시하지 않는다.
- 초기 나염 영역은 앞판·뒤판이다. 소매·후드는 원단/바탕색을 표현하며 나염 부착 영역 추가는 템플릿 확장으로 남긴다.
- PNG/JPEG/WebP 이미지를 업로드해 여러 나염 레이어로 배치한다. 투명 PNG를 보존하고 위치·크기·회전·순서·복제·삭제·숨김, 실행 취소/다시 실행을 제공한다. 직접 텍스트/벡터 편집은 이번 범위에서 제외한다.
- 숫자 입력과 키보드 조작을 드래그 대안으로 제공한다. 회전된 레이어 전체가 인쇄 가능 영역 안에 들어와야 저장할 수 있다. 잘못된 배치를 자동으로 잘라내거나 바꾸지 않는다.
- 3D 회전·확대·정면/후면 복귀. 조명은 고정된 스튜디오 조명으로 시작해 재질 비교가 가능하게 한다.
- 상세에서 저장된 앞/뒤 2D 목업 PNG를 내려받는다. 편집 중 파일 내보내기와 3D 화면 캡처는 초기 범위에서 제외한다. PNG는 sRGB·면별 2048px 정사각 캔버스·투명 배경·의류 도안 포함의 검토용 이미지이며 생산용 출력이 아니다.
- 초기 디자인은 상품 등록 없이 독립 생성한다. 기존 상품 연결/공장 공유/이미지 자동 등록은 하지 않는다. 추후 명시적 연결 작업을 추가한다. 기존 공장 협업 메뉴와 별개인 관리자 디자인 메뉴를 추가한다.

## 화면과 저장 UX

URL 제안: `/admin/designs`(목록), `/admin/designs/new`(생성), `/admin/designs/[id]`(상세), `/admin/designs/[id]/edit`(편집). 목록에 입력 폼을 붙이지 않고 편집 화면에 전체 디자인 목록·전체 이력을 붙이지 않는다.

목록은 공통 페이지네이션, 상세는 이름·템플릿·수정시각·저장 버전·2D/3D 조회와 편집 진입을 제공한다. 편집기는 모바일에서 2D/3D 탭 전환, PC에서는 두 미리보기를 함께 볼 수 있게 구성한다. 모바일에서도 숫자 입력·파일 선택·저장이 가능해야 하며 정밀 드래그만을 유일한 수단으로 삼지 않는다. 공통 토큰/SaveResult를 사용한다.

저장은 수동이다. 변경 후 미저장 상태와 페이지 이탈 경고, 저장 중 중복 제출 차단, 서버 확정 ID/버전/대상과 상세·계속 편집 동작, 완료 제목 포커스를 제공한다. 실패 시 문서와 입력을 유지한다. 서버 저장 성공 후 상세 조회가 실패해도 저장 결과를 지우지 않는다. 새로고침 경고는 브라우저 제약 내 best-effort이며 자동 복구/오프라인 저장은 초기 보장 대상이 아니다.

버전 충돌은 409로 감지하고 로컬 변경을 유지한 채 최신 버전 재조회 또는 별도 새 디자인으로 저장할 수 있게 한다. 원래 문서에 자동 덮어쓰기를 하지 않는다. 응답 불확실 시 같은 request_id와 같은 본문으로 재시도한다.

## 단일 디자인 문서와 확장 계약

DesignDocument v1 = schema_version, template_id/template_version, material_id/material_version, base_color(#RRGGBB), gloss(0..1), decorations[].
Decoration v1 = id(UUID), technique='print', surface_id(front/back), asset_id, center(x,y), size(width,height), rotation_degrees, visible. 배열 순서가 앞뒤 순서다. 모든 숫자는 유한수이며 center는0..1, size는0 초과1 이하, 회전은-180..180. surface 좌표는 좌상단 원점·오른쪽+x·아래+y로 통일한다. 2D 화면 픽셀이나 3D 월드좌표를 저장하지 않는다.

실행 취소/redo와 향후 3D hit-test는 같은 문서 명령(레이어 이동/크기/회전)을 호출한다. 카메라 상태·선택·패널 상태는 문서의 생산/디자인 데이터와 구분한다.

TemplateDefinition = 고정 ID/버전, 2D 윤곽·인쇄 영역, 면 ID, UV 매핑, 3D 모델 공급자, 원단 슬롯, 장식 capability. 초기 두 템플릿은 프로젝트에서 직접 제작한 기본형 mesh와 대응 도안을 사용한다. 저작권 불명 모델이나 원격 모델을 임의 다운로드하지 않는다. 목·소매·후드 실루엣을 가진 실제 입체 형상이어야 하며 평면 그림을 회전시키는 것으로 대체하지 않는다.

같은 면의 합성 텍스처를 2D와 3D UV에 사용한다. 후면 좌우 뒤집힘·가슴/등 위치·경계 오염을 표식 이미지로 검증한다. 면별 인쇄 영역은 명시적 정규화 사각형이며 목/봉제선/후드 주머니를 침범하지 않는 보수적인 범위로 설정한다.

후속 사용자 의류 모델은 GLB와 면/UV/인쇄영역 정의를 등록하는 공급자로 추가하도록 경계를 둔다. 이번에는 임의 GLB 업로드 UI를 구현하지 않는다. 신규 템플릿 추가가 기존 렌더러에 의류명 조건문을 추가하도록 만들지 않는다. 템플릿 버전은 불변이며 기존 문서는 옛 템플릿을 보존한다. 편집 중 템플릿 교체는 제공하지 않고 새 디자인 생성으로 전환한다.

MaterialDefinition의 appearance(색/roughness/표면 요철)와 향후 physical properties(신장/굽힘/밀도)는 별도 모델로 둔다. 초기에는 physical 필드를 입력/저장/계산하지 않는다. gloss를 roughness로 매핑하되 비금속 원단을 기본으로 한다. 나염 합성 후에도 표면 질감과 광택이 유지되도록 원단 요철과 색상 텍스처를 분리한다.

장식 방식은 technique 식별자와 등록된 renderer/validator 계약을 가진다. 초기 allowlist는 print뿐이며 자수·패치 UI를 작동하는 것처럼 표시하지 않는다. 미지원 문서 버전/장식 방식은 읽기 오류를 명시하고 손실 저장하지 않는다.

## 저장·권한·API 경계 — 구현자 제안

초기 관리자 역할은 기존 서버 관리자 인증을 사용한다. 개인별 디자이너 소유권이 이미 있다고 가정하지 않는다. 공장/고객 토큰은 프로젝트·자산·버전에 접근하지 못한다. BFF는 관리자 세션과 쓰기 요청 Origin을 검증하며 API에서 다시 인증/관계를 검사한다.

기존 catalog DB와 분리된 worktree .local/designs.sqlite3에 DesignProject, immutable DesignVersion, DesignAsset, request receipt를 저장한다. DB 경로는 이 worktree에 귀속하며 원본 DB를 열지 않는다. 작은 로컬 범위의 검증된 이미지 바이트도 해당 DB에 저장한다. 운영 저장소 전환은 별도 ADR 대상이다. 원단/템플릿 정의는 버전 고정 registry로 서버 검증에 사용한다.

API prefix /api/v1/admin/designs, BFF /api/admin/designs:
- GET templates, GET materials: 허용 ID/버전·면·제한과 표시 metadata.
- GET /: page/size(10/20/50/100)·이름 검색, 최신 저장 요약. POST /: request_id·이름(1..120)·template_id/version, 빈 디자인과 version=1을 원자 생성.
- GET /{id}: 최신 canonical document와 version, 자산 metadata. PATCH /{id}: request_id/base_version/name/document, 자산 소속·템플릿·좌표·개수 검증 후 immutable version 추가와 최신 포인터를 원자 갱신.
- POST /{id}/assets: request_id·image data, 검증·재인코딩 후 asset metadata. GET /{id}/assets/{asset_id}: 관리자 인증 후 이미지 반환. 다른 프로젝트 자산 참조 금지.
- POST /{id}/copies: request_id·현재 로컬 document와 name, 모든 참조 자산을 서버가 검증/복제하며 독립 project로 원자 저장. 충돌 시 변경 보존용 경로.

동일 request_id/동일 payload는 같은 결과, 다른 payload는409. 버전 검사 전에 동일 요청 receipt를 조회해 응답 분실 재시도가 충돌하지 않게 한다. 불변 버전 및 참조 자산은 초기 삭제하지 않는다. 프로젝트 삭제·버전 복원·버전 비교 UI는 초기 범위에서 제외한다.

한 디자인 최대20레이어, 이미지 원본과 정제 PNG 각각2MiB·최대4096변·16MP, 프로젝트별 최대40자산/40MiB 처리 후 바이트. PNG/JPEG/WebP 단일 프레임만 허용, SVG/URL 불허. 파일 원본 대신 검증/재인코딩한 픽셀 원본을 보존해 EXIF/실행 콘텐츠를 제거한다. 업로드 실패/미사용 자산도 상한에 포함하며 한도 초과 시 명시 안내한다. GC/삭제 정책 없이 자산을 조용히 삭제하지 않는다.

문서 요청 JSON은256KiB, 업로드 요청은 기존 base64 전송을 고려한3MiB로 제한한다. 인증 및 요청 길이를 파싱/이미지 해독 전에 검사한다. 서버는 strict 타입·unknown field·UUID·범위·참조를 검증한다. 401/403/404/409/422 및 크기 초과 응답을 기존 API 패턴에 맞춘다. 비밀·이미지 본문은 로그에 남기지 않는다.

DB schema 버전·트랜잭션 마이그레이션을 사용하고 변경 전 SQLite backup을 확보한다. 초기 롤백은 신규 기능 접근을 중지하고 전용 DB/자산을 보존하는 방식이다. 기존 상품/재고 DB 변경 없음.

## 렌더링 오류와 성능

Canvas 합성 → CanvasTexture 업데이트, 3D는 변경·카메라 조작 시 렌더링한다. 이미지 해독은 비동기로 처리하고 늦게 끝난 이전 로드가 최신 선택을 덮어쓰지 않게 한다. GPU texture/geometry/material·이벤트·object URL을 해제한다. 텍스처는 면별 최대2048px, 모바일 미리보기1024px로 시작하며 내보내기는2048px로 다시 합성한다.

3D 미지원/로딩 실패/context loss는 별도 오류와 재시도·2D 계속 사용을 제공하고 편집 내용을 유지한다. 3D 실패를 저장 실패로 표현하지 않는다. 초기 타깃은 현재 Windows Edge/Chrome, 모바일 반응형을 실제 브라우저에서 확인한다. 성능 목표는 검증 기기의 사양과 함께 편집 반영200ms 이내·회전30fps 이상을 측정하며 미달 시 결과를 숨기지 않는다. 보장 수치로 선기재하지 않는다.
