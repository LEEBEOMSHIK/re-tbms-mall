# 내부 관리명·고객 표시명 및 카테고리 선택

2026-10-26 / WB15 / R03·R18·R31·R32

## 요구와 구현 선택

사용자 요구는 내부와 고객용 상품명을 구분하고 카테고리·등록 순번에 따른 내부명 자동 생성 및 카테고리 콤보박스를 제공하는 것이다. 단일 상품명을 두 입력란에 복제하는 대신 서버가 내부 관리명을 발급하고 고객 표시명만 직접 입력한다.

구현 선택: 카테고리 코드+카테고리별 6자리 이상 증가 순번(TOP-000001). 순번은 서버 저장 시 트랜잭션으로 확정한다. 화면은 예상 번호를 예약하거나 확정값처럼 표시하지 않는다. 발급된 내부 관리명은 분류·고객 표시명 수정 후에도 유지한다. 초기 분류는 상의/TOP, 아우터/OUT, 하의/BTM, 원피스/DRS, 기타/ETC이며 최종 사업 분류의 확정은 아니다. 기존 자유 입력 분류는 보존해 선택지로 이관한다. 카테고리 추가/수정 UI는 이번 범위가 아니다.

## 계약·데이터

GET /api/v1/admin/catalog: categories:[{id,name,code}] 추가. Product는 기존 name(고객 표시명), category(표시용 분류 이름)에 internal_name, category_id 추가. 생성/수정 입력은 name, category_id, description, 수정 시 version이다. category 자유 입력과 internal_name 직접 지정은 거절한다. 같은 카테고리 동시 등록은 서로 다른 순번을 발급하며 재시작 후에도 계속 증가한다.

SQLite user_version 1→2: 기존 상품·옵션·재고·원장 ID와 데이터를 보존하는 트랜잭션 마이그레이션. 기존 상품 순서는 저장된 rowid 기준(정확한 과거 시각을 새로 만들어내지 않음). 기존 미지정 분류는 독립 이관 분류로 보존한다. 알 수 없는 스키마는 자동 초기화하지 않는다. 오류 시 v1 변경을 롤백한다. 원래 발급 카테고리 기반 내부명은 이후 변경하지 않는다.

## 담당과 단계

1. 조정 담당: 기존 실제 DB SQLite 온라인 백업 확인, 계획·요구·결정·데이터·API·README·보드. 백업 .local/catalog-before-v2-20261026-010319.sqlite3 (schema1).
2. inventory_api: services/api/app/inventory.py와 tests/test_inventory.py 등 API 소유. 마이그레이션·분류·원자적 번호 발급과 검증. UI와 계약 조율.
3. inventory_ui: apps/web/src/lib/catalog.ts, tests/catalog.test.ts와 catalog 화면 소유. 고객 표시명 입력, 분류 select, 읽기 전용 내부명, 목록/선택지 두 이름 표시. 미게시·별도 등록 화면 유지.
4. inventory_review: 별도 검토·테스트. 조정 담당은 실제 브라우저 통합 후 완료 처리.

## 수용·검증 기준

- 상품 목록/수정/등록 결과에서 두 이름의 의미가 구분된다.
- 신규 내부명은 실제 저장 결과만 표시하고 분류 선택과 같은 입력으로 동시 등록 시도에도 중복되지 않는다.
- 분류 select는 서버 제공 값만 사용하며 조작한 category_id와 내부명 입력을 서버가 거절한다.
- 수정 후 내부명 고정, 기존 이름/재고/원장 보존, v1 이관과 재시작 계속 증가 검증.
- 웹 테스트·lint·타입·빌드 및 Edge 생성·수정·분류·모바일 확인.

## 복구와 제한

마이그레이션은 상품 게시를 수행하지 않는다. 기존 고객 샘플/대시보드는 별도 유지한다. 복구는 API를 중지하고 현재 DB도 추가 백업한 후 코드 버전과 호환되는 백업 DB로 교체한다. v1 백업 복구 시 v2 이후 입력은 먼저 보존·재적용해야 한다. 백업을 무조건 덮어쓰거나 DB를 삭제하지 않는다. 운영 DB·실거래·카테고리 관리 UI·커밋/푸시는 이번 범위가 아니다.
