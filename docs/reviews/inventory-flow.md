# WB41 재고 흐름·선택 메모 검증

- 요구사항: R51 / 검증일: 2026-10-26
- 구현: inventory_api(API), inventory_ui(UI), 조정 담당(계약·문서)
- 독립 검증: inventory_review

## 변경과 결과

상세 사유는 선택 문자열이며 생략·빈칸·공백을 허용한다. 최대 300자와 null 거부는 유지한다. 서버에서 저장을 확인한 뒤 `/admin/catalog/inventory?saved=<원장 ID>`로 이동한다. 목록 GET에서 해당 원장이 확인되고 조회 오류가 없을 때만 SKU·증감·전후 수량을 안내하고 제목으로 포커스를 이동한다. 쿼리 값만으로 성공을 표시하지 않는다.

조회 흐름은 입고, 고객 출고(판매), 기타 출고·조정, 기존 기록·미분류다. 흐름 변경 시 세부 사유 필터를 초기화한다. 증정·폐기는 판매로 분류하지 않는다. 같은 SKU 보유 수량과 원장을 사용하며 별도 재고를 중복 집계하지 않는다.

## 실행한 검증

- 독립 API 테스트: 197개 통과. 선택 메모, 길이·null 경계, 동일 요청 재시도 및 변경 충돌 포함.
- 독립 웹 테스트: 51개 통과. 빈 메모 원장 파싱 및 확인 계약 포함.
- 독립 lint, typecheck, production build: 모두 exit 0.
- Edge 실제 브라우저 + 모의 API: 빈 메모 저장, 503 후 동일 요청 재시도, 확정 후 자동 이동, 목록 조회 실패 시 성공 안내 없음, 재조회 시 실제 원장 결과·포커스 확인.
- 네 흐름 필터, 알 수 없는 saved ID의 확인 불가 안내, 320px·390px 문서 가로 넘침 없음 확인.
- 브라우저 성공 쓰기는 모의 응답으로 처리했으며 실제 재고는 변경하지 않았다.

## 파일과 한계

변경 대상: services/api의 재고 요청 스키마·테스트, apps/web의 catalog 계약·테스트, 재고 폼·목록·관리자 연결·inventory 페이지, 요구사항·API·디자인·결정 문서.

현재 구분은 기존 사유 코드에 따른 관리 보기다. 실제 공장/공급처, 발주·검수, 고객/주문별 배송 정보 연동은 미구현이며 별도 설계가 필요하다. 운영 통합·실거래 테스트는 수행하지 않았다. DB 스키마 변경은 없으며 복구는 이번 코드·문서 변경만 되돌리는 방식이다.
