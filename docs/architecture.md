# 기본설계서 v0.3

## 구조

Next.js 고객·관리자·시안 웹 → FastAPI API → 관계형 DB(제품 미정).

상품 이미지는 공개 읽기 정책의 객체 저장소·CDN 후보로, 시안·문의 첨부는 비공개 저장소 정책으로 분리한다. 느린 이미지 처리·향후 AI·알림·대사는 작업 큐/워커 후보로 둔다. 로컬은 Docker 없이 직접 실행하고 운영은 Docker 기반으로 배포한다. DB·큐·저장소·인증 제품과 버전, 운영 호스트·오케스트레이션은 아직 선택하지 않았다. 상세 실행·검증 기준은 [환경 정책](environments.md)을 따른다.

대안은 상용 쇼핑몰 활용, 모듈형 자체 개발, 초기부터 마이크로서비스 분리다. 사용자 지정 Next.js·FastAPI를 기준으로 모듈형 자체 개발을 제안한다. 거래 일관성과 운영 단순성이 이유다. 상용 플랫폼 연계와 서비스 분리는 필요·규모·비용 근거가 생길 때 ADR로 재검토한다.

## 서버 모듈 경계

| 모듈 | 소유 책임 |
|---|---|
| catalog | 상품·카테고리·옵션·SKU·이미지·실측 |
| pricing | 가격 이력·프로모션·쿠폰·견적 |
| inventory | 재고 원장·예약·할당·입출고·검수 |
| orders | 주문·품목·주소/정책 스냅샷·수량 집계 |
| payments | 조건부 PG 승인·조회·환불·외부 거래 |
| fulfillment | 출고 작업·배송 묶음·운송장·배송 이벤트 |
| claims | 취소·반품·교환·검수·비용 판단 |
| identity | 사용자·동의·역할·권한 |
| settlement | 조건부 PG 거래·수수료·정산·입금 대사 |
| support | 문의·답변·내부 메모 |
| designs | 시안 프로젝트·버전·자산·검토·상품 연결 |
| notifications | 조건부 채널·템플릿·발송·결과 |
| audit | 민감 작업·변경 기록 |

다른 모듈의 테이블을 임의 수정하지 않는다. 교차 업무는 애플리케이션 서비스가 트랜잭션과 이벤트를 조정한다. 재고·가격·권한을 Next.js와 FastAPI에 중복 구현하지 않는다. 프론트 검증은 안내이며 서버가 최종 판정한다.

## 구현 디렉터리 후보

향후 `apps/web`, `services/api`, `docs` 구성을 제안한다. 지금은 문서만 생성한다. FastAPI 내부는 모듈별 API 스키마·업무 서비스·데이터 접근을 분리하고 HTTP·PG SDK에 업무 규칙을 직접 묶지 않는다. Next.js에서 서버 전용 비밀값과 브라우저 공개 데이터를 분리한다.

## 웹·모바일·앱

고객 웹은 모바일 우선으로 핵심 흐름 전체를 지원한다. 관리자 모바일은 조회·간단한 변경부터 범위를 정의한다. 시안의 정밀 편집은 터치·확대·이동을 고려하되 전체 모바일 기능 지원은 Q02에서 결정한다.

향후 앱은 같은 FastAPI 계약을 사용한다. 인증은 브라우저 세션 보호와 모바일 토큰 저장·갱신 요구를 비교해 선택한다. PWA·웹뷰·React Native·네이티브 앱 중 어느 것도 확정하지 않았다. Next.js 화면이 자동으로 네이티브 앱이 되는 것으로 가정하지 않는다.

## 시안 프로그램

초기 후보는 2D 템플릿 위 색상·텍스트·로고 배치, 버전 저장·복제·비교·내보내기다. 3D 착용, AI 생성, 생산 패턴 CAD는 서로 다른 범위다. 시각적 목업이 실제 생산 가능한 패턴임을 보장하지 않는다.

편집 데이터는 이미지 결과만이 아니라 문서 버전·캔버스 규격·레이어 순서·변환·참조 자산을 함께 저장하는 방안을 제안한다. 데이터 포맷 버전과 이전 버전 읽기 정책을 정한다. 내보내기 크기·색공간·폰트·투명도·앞/뒤면 지원은 편집기 상세설계 전에 결정한다.

저장 충돌은 버전 비교로 감지하고 다른 사용자의 작업을 덮어쓰지 않는다. 원본 자산은 보존한다. 삭제·보관 정책과 외부 공유 여부는 권한·저작권 검토에 맞춘다. 승인 시안은 상품 초안에 연결하되 게시 상품·SKU·재고 변경은 별도 작업이다.

## AI 확장

AI는 현재 구현 필수가 아니다. 도입 시 제공자 어댑터, 비동기 작업 ID, 진행·실패·취소 상태, 비용 한도, 실행 권한, 모델·생성 조건·원본 추적을 둔다. 외부 전송·학습 이용·보관 조건을 검토한다. 결과가 재고·가격·상품 설명에 검토 없이 확정 반영되지 않게 한다.

## 성능·관측성·복구 제안

초기 검증 기준은 상품 1만·SKU 10만, 조회 50요청/초·체크아웃 5요청/초를 30분 유지하는 시나리오다. 체크아웃은 거래 단계에서만 적용한다. 내부 조회 p95 500ms, 변경 p95 1초(외부 처리 제외), 모바일 실제 사용자 p75 LCP 2.5초·INP 200ms·CLS 0.1을 목표 후보로 한다.

월 가용성 99.9%, RPO 15분·RTO 4시간은 비용·인프라·복원 실험 전의 제안이다. 서비스 측정 경계·유지보수·외부 장애 포함 여부를 정의한다. 현재 성능 측정 또는 보장은 없다.

관측 대상: API 지연·오류, DB 잠금, 큐 적체, 재고 불일치, 결제/환불 미확정, 출고 지연, 대사 차액, 시안 저장 실패·내보내기 지연, 알림 실패, 관리자 이상 접근. 추적 ID로 연결하되 개인정보·비밀값을 기록하지 않는다.

상품 이미지 크기·지연 로딩·캐시, 상품 URL·메타데이터·사이트맵·필터 색인 정책을 설계한다. 캐시는 주문 가격·재고의 최종 근거가 아니다.
