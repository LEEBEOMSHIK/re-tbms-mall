# 에이전트 작업·검증 절차 v0.3

## 역할과 소유권

| 역할 | 책임·기본 파일 범위 | 인수인계 대상 |
|---|---|---|
| 조정·요구 담당 | 요구·결정·작업 명세·의존성·범위 | 모든 담당자 |
| 아키텍처/API 담당 | 모델·상태·계약·마이그레이션 설계 | FE·BE·시안·검증 |
| 프론트 담당 | Next.js 고객·관리자 화면 | 디자인·API·검증 |
| 백엔드 담당 | FastAPI 서비스·권한·재고·거래 | API·통합 검증 |
| 시안 담당 | 편집 데이터·자산·버전·출력 | 디자인·BE·검증 |
| 디자인 시스템 담당 | 토큰·공통 컴포넌트·접근성 | FE·시안·검증 |
| 독립 검증 담당 | 변경 리뷰·요구 충족・정합성·회귀 | 구현 담당·조정 담당 |
| 운영·보안 담당 | 배포·비밀·관측·복구·개인정보 | 통합 검증·운영자 |

역할은 논리적 책임이며 특정 도구의 에이전트 설정을 설치한 것은 아니다. 작은 작업은 역할을 겸임할 수 있지만 최종 검증은 작성자와 분리한다. 검증자를 실행할 수 없으면 미수행을 기록하고 사람의 리뷰를 받는다.

## 상태와 관문

`정의 중 → 준비 완료 → 구현 중 → 자체 검증 → 독립 검증 → 통합 검증 → 완료`

결함 발견 시 구현 중으로 되돌린다. 보류에는 사유·선행 결정·담당자·재개 조건을 기록한다.

1. **정의:** 요구 ID·화면·데이터·API·업무 정책·수용 기준을 [작업 명세](templates/task.md)에 기록한다.
2. **준비 완료:** 선행 계약이 일치하고 해당 작업의 필수 미정 사항이 해소되었다. 임시 모의 범위는 명시한다.
3. **구현:** 소유 파일과 범위 안에서 작업하고 공유 계약 변경은 먼저 조율한다. 기존 사용자 변경을 보존한다.
4. **자체 검증:** 변경에 맞는 단위·계약·통합·수동 검증을 실행한다. 실패·미실행을 숨기지 않는다.
5. **독립 검증:** 다른 검증자가 실제 diff, 요구, 실행 증거를 읽고 필요한 재현을 수행한다. 요구 누락과 심각 결함은 다음 관문을 막는다.
6. **통합 검증:** 조정 담당이 결합된 변경에 대해 대표 흐름과 회귀를 검증한다. 개별 통과만으로 통합 성공을 선언하지 않는다.
7. **완료:** 문서·변경 기록·미정·복구 절차를 맞추고 [검증 보고서](templates/review.md)를 남긴다. 게시·배포는 별도 승인 범위다.

## 병렬 작업 규칙

먼저 API·스키마·토큰 계약을 정한다. 각 작업의 파일 소유권·공유 파일 담당자·통합 순서를 기록한 뒤 독립 작업만 병렬 실행한다. 동일 파일 동시 수정은 조정 담당이 순서를 지정한다. 모든 작업에 새 작업 트리를 만드는 것을 요구하지 않으며 현재 저장소 상태와 도구 제약에 맞춰 격리한다.

예시: 상품 API 계약 완료 후 BE의 상품 조회와 FE의 모의 데이터 화면 작업을 분리한다. 실제 통합 시 API 예제·오류·옵션·품절 상태까지 확인한다. 재고 불변식이 미정인 상태에서 서로 다른 에이전트가 각각 재고 규칙을 정하지 않는다.

## 검증자 지시문

작업 ID와 요구 ID를 읽고 변경 파일·API/모델 계약·실행 결과를 확인한다. 합의하지 않은 기능, 권한 누락, 금액·수량 불일치, 복구 불가능 상태, 디자인 예외를 찾는다. 문제별 심각도·재현 조건·근거 위치·영향·수정 후 검증을 보고한다. 코드 작성자의 요약만으로 통과시키지 않는다. 실제 실행하지 않은 항목은 미실행으로 남긴다.

출시 차단 결함은 정보 노출·이중 결제·초과 판매·데이터 손실·법정 절차 차단 등이다. 심각도 판단과 잔여 위험 수용자는 보고서에 기록한다.

## 문서·명령 운영

새 선택은 결정 기록 또는 ADR에 상태·대안·근거·영향을 남긴다. 실행 환경을 구성한 뒤 실제 검증한 개발·테스트·빌드 명령을 README에 추가한다. 지금 단계에는 실행 가능한 앱·CI가 없으며 문서의 테스트 계획을 테스트 통과 결과로 표현하지 않는다.
