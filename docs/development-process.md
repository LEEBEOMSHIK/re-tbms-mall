# 에이전트 작업·검증 절차 v0.3

## 역할과 소유권

| 역할 | 책임·기본 파일 범위 | 인수인계 대상 |
|---|---|---|
| 조정·요구 담당 | 요구·결정·작업 명세·의존성·범위 | 모든 담당자 |
| 아키텍처/API 담당 | 모델·상태·계약·마이그레이션 설계 | FE·BE·시안·검증 |
| 프론트 담당 | Next.js 고객·관리자 화면 | 디자인·API·검증 |
| 백엔드 담당 | FastAPI 서비스·권한·재고·거래 | API·통합 검증 |
| 시안 담당 | 편집 데이터·자산·버전·출력 | 디자인·BE·검증 |
| 디자인 시스템 담당 | 토큰·공통 컴포넌트·접근성 | FE·시안·검증 |
| 독립 검증 담당 | 변경 리뷰·요구 충족・정합성·회귀 | 구현 담당·조정 담당 |
| 운영·보안 담당 | 배포·비밀·관측·복구·개인정보 | 통합 검증·운영자 |

역할은 논리적 책임이며 특정 도구의 에이전트 설정을 설치한 것은 아니다. 작은 작업은 역할을 겸임할 수 있지만 최종 검증은 작성자와 분리한다. 검증자를 실행할 수 없으면 미수행을 기록하고 사람의 리뷰를 받는다.

## 상태와 관문

`정의 중 → 준비 완료 → 구현 중 → 자체 검증 → 독립 검증 → 통합 검증 → 완료`

결함 발견 시 구현 중으로 되돌린다. 보류에는 사유·선행 결정·담당자·재개 조건을 기록한다.

1. **정의:** 요구 ID·화면·데이터·API·업무 정책·수용 기준을 [작업 명세](templates/task.md)에 기록한다.
2. **준비 완료:** 선행 계약이 일치하고 해당 작업의 필수 미정 사항이 해소되었다. 임시 모의 범위는 명시한다.
3. **구현:** 소유 파일과 범위 안에서 작업하고 공유 계약 변경은 먼저 조율한다. 기존 사용자 변경을 보존한다.
4. **자체 검증:** 변경에 맞는 단위·계약·통합·수동 검증을 실행한다. 실패·미실행을 숨기지 않는다.
5. **독립 검증:** 다른 검증자가 실제 diff, 요구, 실행 증거를 읽고 필요한 재현을 수행한다. 요구 누락과 심각 결함은 다음 관문을 막는다.
6. **통합 검증:** 조정 담당이 결합된 변경에 대해 대표 흐름과 회귀를 검증한다. 개별 통과만으로 통합 성공을 선언하지 않는다.
7. **완료:** 문서·변경 기록·미정·복구 절차를 맞추고 [검증 보고서](templates/review.md)를 남긴다. 게시·배포는 별도 승인 범위다.

## 병렬 작업 규칙

먼저 API·스키마·토큰 계약을 정한다. 각 작업의 파일 소유권·공유 파일 담당자·통합 순서를 기록한 뒤 독립 작업만 병렬 실행한다. 동일 파일 동시 수정은 조정 담당이 순서를 지정한다. 모든 작업에 새 작업 트리를 만드는 것을 요구하지 않으며 현재 저장소 상태와 도구 제약에 맞춰 격리한다.

예시: 상품 API 계약 완료 후 BE의 상품 조회와 FE의 모의 데이터 화면 작업을 분리한다. 실제 통합 시 API 예제·오류·옵션·품절 상태까지 확인한다. 재고 불변식이 미정인 상태에서 서로 다른 에이전트가 각각 재고 규칙을 정하지 않는다.

## 별도 worktree 준비·통합·정리 절차

1. 원본 HEAD·브랜치·인덱스와 미커밋 파일을 확인한다. 기존 staged 상태를 바꾸는 stash/reset/checkout 없이, 별도 임시 인덱스와 로컬 스냅샷 ref로 추적 파일 및 선별한 미추적 소스를 보존할 수 있다. 원본 파일이 스냅샷 생성 중 바뀌면 해시 재확인 후 다시 준비한다.
2. 관리형 worktree를 스냅샷에서 생성하고 작업용 codex/ 브랜치를 사용한다. 생성 후 원본 HEAD/인덱스 불변, 소스 일치, 비밀·실행 데이터·캐시 제외를 확인한다. workboard.md에는 기준 커밋, 경로, 담당과 검증 근거를 남긴다. 다른 worktree의 보드는 기준 시점 사본이며 상태 원본을 별도로 운영하지 않는다.
3. 추가 작업의 범위·수정 파일·API 계약을 먼저 정한다. 공통 파일과 원본 workboard.md는 조정 담당만 갱신한다. 작업용 DB/업로드/환경변수/포트는 별도 구성하고 원본 프로세스를 중지하지 않는다. 의존성은 해당 worktree에 설치하며 원본 node_modules/.venv를 연결하지 않는다.
4. 통합 직전 원본의 최신 변경을 보존하고 작업 브랜치의 기준 스냅샷 이후 커밋만 검토·통합한다. 원본이 아직 dirty라면 바로 merge/cherry-pick하지 말고 보존 및 통합 기준부터 확보한다. 스냅샷 전체를 기능 변경으로 다시 적용하거나 폴더를 덮어쓰지 않는다. 충돌 파일은 양쪽 의도를 반영하고 독립 검증·대표 흐름 회귀를 수행한다.
5. 통합 검증 뒤 해당 작업의 임시 출력·중복 파일·캐시를 참조/사용 여부에 따라 선별한다. 필수 소스·잠금 파일·검증 기록·사용자 자산·원본 DB는 보존한다. 생성/보존 출처가 불명확한 파일은 삭제하지 않는다.
6. 사용 중 프로세스와 미통합 변경, ignored 고유 자료가 없음을 확인한 뒤 사용이 끝난 관리형 worktree를 archive_worktree로 정리한다. 이는 복구 스냅샷을 남기며 원본 작업 폴더를 삭제하지 않는다. 임시 인덱스 등 자신이 만든 파일만 정확한 절대경로를 검증해 제거한다. 스냅샷 ref/작업 브랜치는 통합 및 복구 가능성을 확인한 뒤 정리하며 강제 branch 삭제는 하지 않는다.
7. 작업 카드에 통합 대상 커밋·실제 검증·정리 경로·보존/미정리 사유·복구 방법을 기록한다. 정리 예정과 정리 완료를 구분한다. 게시·푸시·배포는 별도 승인 범위다.

## 독립 검증자 지시문

작업 ID와 요구 ID를 읽고 변경 파일·API/모델 계약·실행 결과를 확인한다. 합의하지 않은 기능, 권한 누락, 금액·수량 불일치, 복구 불가능 상태, 디자인 예외를 찾는다. 문제별 심각도·재현 조건·근거 위치·영향·수정 후 검증을 보고한다. 코드 작성자의 요약만으로 통과시키지 않는다. 실제 실행하지 않은 항목은 미실행으로 남긴다.

출시 차단 결함은 정보 노출·이중 결제·초과 판매·데이터 손실·법정 절차 차단 등이다. 심각도 판단과 잔여 위험 수용자는 보고서에 기록한다.

## 문서·명령 운영

새 선택은 결정 기록 또는 ADR에 상태·대안·근거·영향을 남긴다. 실행 환경을 구성한 뒤 실제 검증한 개발·테스트·빌드 명령을 README에 추가한다. 현재 기본 앱과 로컬 개발 명령은 README를, 실제 실행 결과는 검증 기록을 따른다. 업무 기능·CI·운영 배포가 구현되었다고 확대 해석하지 않는다.

## Markdown 작업 보드 운영

루트 [workboard.md](../workboard.md)를 작업 상태의 기준으로 사용한다. 조정 담당이 작업 시작 시 담당/선행 조건/완료 기준을 확인하고 진행 상태로 갱신하며, 구현 완료 후에는 검증 중임을 기록한다. 독립·통합 검증 근거를 남긴 뒤 완료 처리한다. 다음 작업 제안 및 사용자 결정 필요 항목은 승인이나 실행 완료로 간주하지 않는다.

각 작업의 검증 필드에는 실행 결과와 관련 계획·검증 기록의 상대 경로를 남긴다. 작업 종료 시 갱신일 및 미정 사항을 함께 정리한다. 사용자와 에이전트가 같은 파일을 관리하며 병렬 작업 중에는 조정 담당 한 명이 병합한다. 문서 형식과 확인 방법은 [작업 보드 안내](workboard.md)를 따른다.

## UI/UX 피드백 반영 절차

사용자 UI/UX 수정 요청은 해당 화면의 일회성 CSS 변경으로 끝내지 않는다. 공통 패턴에 해당하면 docs/design-system.md에 최신 기준·토큰·컴포넌트·적용 화면을 갱신하고 실제 공통 구현에도 반영한다. 이후 새 화면은 공통 폼 스타일/컴포넌트를 먼저 사용하며 페이지별 모서리·상태를 재정의하지 않는다.

1. 피드백이 화면 고유인지 공통 규칙인지 판단하고 작업 명세에 기록한다.
2. 공통이면 토큰/컴포넌트를 수정하고 영향을 받는 입력·선택·비활성·읽기전용 상태를 함께 확인한다.
3. 대표 PC/모바일 화면과 키보드 조작을 검증한다. 예외가 필요하면 이유와 적용 화면을 디자인 문서에 남긴다.
4. 완료 시 실제 적용 범위와 미적용 화면, 검증 근거를 기록한다. 문서에만 규칙을 추가한 것을 공통화 완료로 표현하지 않는다.

## 쓰기 화면 완료 UX 검증 관문

신규/수정/입고/조정 등 저장 작업이 포함되면 docs/design-system.md의 저장·수정 완료 규칙을 작업 명세 수용 기준에 넣는다. 공통 SaveResult 또는 동등한 결과 영역을 사용하고 예외는 사유를 기록한다. 독립 검증자는 실제 저장 후 대상/변경 내용/다음 행동이 보이는지, 모바일 하단 제출 후 완료 제목 포커스, 중복 클릭, 실패 입력 보존, 응답 불확실 및 저장 성공·조회 실패 구분을 확인한다. 필요한 항목 미확인 상태는 완료로 넘기지 않는다. 단순 토스트/입력 초기화만으로 성공 피드백을 충족했다고 판단하지 않는다.

## 목록·입력 분리 검증 관문

모든 관리화면 신규/수정 작업은 목록·등록·수정 화면을 분리하는 디자인 규칙을 수용 기준에 넣는다. 검증자는 목록에서 작성 폼이 없고 입력에서 전체 이력/목록이 없는지, 각 화면 URL·인증·등록 진입·목록 복귀·완료 후 이동이 연결되는지 확인한다. 입력 검토용 대상 요약과 전체 목록을 구분한다. 예외는 작업 명세의 이유와 검증 근거가 있어야 한다. 화면 분리 확인을 생략한 채 완료로 처리하지 않는다.

## 관리자 사용 가이드 갱신
관리자 기능 작업의 영향 분석에서 apps/web/src/lib/admin-guide.ts의 relatedPaths와 설명/링크를 확인한다. 새 메뉴·경로·입력·업무 순서·저장 결과·실패 복구가 바뀌면 같은 작업에서 가이드 항목을 수정하고 UI/API 확인 날짜(updatedAt)를 기록한다. 작업 명세에는 영향 가이드 ID를, 검증서에는 실제 변경/링크 확인 결과를 남긴다. 영향 없으면 이유를 기록한다. node --test tests/admin-guide.test.ts (apps/web에서)로 링크/구조를 검사한다. 이 검사는 의미상 절차 정확성을 자동 보장하지 않으므로 독립 검증자가 실제 화면/코드와 비교한다. 가이드 동기화 누락은 완료 조건 미충족이다.
# 실제 화면 가이드 유지 (WB115)
관리자 기능 변경 시 `admin-guide.ts` 원문과 `admin-guide-captures.ts` 단계 키를 함께 확인한다. 버튼 위치·이름·업무 흐름에 영향이 있으면 합성 데이터로 캡처를 교체하고 표식을 갱신한다. 자동 자산/좌표 검사 외에 이미지와 클릭 영역의 시각 일치, 확대·모바일·인증을 검증 기록에 남긴다. 캡처를 public으로 옮기지 않는다.
