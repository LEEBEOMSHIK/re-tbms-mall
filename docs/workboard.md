# 공유 작업 보드 관리 안내

작업 목록의 단일 원본은 저장소 루트 [workboard.md](../workboard.md)이다. 이 안내 문서에는 작업 상태를 중복 기록하지 않는다.

- 보드 및 원문 보기: http://127.0.0.1:3100/admin/workboard
- Markdown 원문 전용: http://127.0.0.1:3100/admin/workboard/source

파일을 편집·저장하고 브라우저를 새로고침하면 같은 파일이 반영된다. 별도 JSON 수정이나 복사/생성 절차가 없다. 웹 화면은 읽기 전용이며 자동 에이전트 실행 감시가 아니다.

## 작성 형식

문서 첫 제목은 `# 보드 제목`이다. 문서 메타데이터는 다음 세 줄을 사용한다.

```markdown
- 갱신일: 2026-10-25
- 검증일: 2026-10-25
- 검증 요약: 실제 확인한 결과와 남은 제한
```

작업마다 고유 ID를 붙이고 다음 필드를 모두 작성한다. 아래는 형식 예시이며 현재 작업이 아니다.

```markdown
### WB10 | 작업 제목
- 상태: next
- 담당: 구현 담당 / 독립 검증 담당
- 우선순위: P1
- 내용: 사용자 요청과 작업 범위
- 완료 기준: 검증 가능한 결과
- 선행 조건: 선행 작업 ID 또는 결정할 사항
- 검증: 착수 전. 계획: docs/superpowers/plans/해당-계획.md
```

상태는 `in-progress`(구현·검증 중), `next`(다음 제안), `decision`(사용자 결정 필요), `done`(검증 완료)만 사용한다. 우선순위는 P0–P3다. 각 필드는 한 줄로 작성하며 값 안의 콜론은 사용할 수 있다. 작업 ID와 필드를 중복하지 않는다. `##`로 그룹을 나누거나 일반 설명을 추가할 수 있고, 추가 설명은 원문 보기에서 확인한다. 필수 필드 누락·알 수 없는 상태는 화면에 문서 오류로 표시되므로 형식을 바로잡은 뒤 새로고침한다.

## 관리 절차

1. 착수 전 현재 작업·의존성·미정 사항을 확인한다. 조정 담당이 작업 ID, 담당, 우선순위, 완료 기준을 기록한다.
2. 착수하면 `in-progress`로 옮긴다. 구현 후 검증 중이라는 사실과 실제 실행 결과를 검증 필드에 남긴다.
3. 독립·통합 검증 후에만 `done`으로 변경한다. 관련 계획과 검증 보고서의 저장소 상대 경로를 남긴다.
4. 갱신일·검증일·검증 요약을 실제 수행 내용에 맞춘다. 다음 제안과 미정 사항을 완료로 만들지 않는다.
5. 병렬 에이전트는 조정 담당에게 보고하고 한 명이 원본을 병합한다. 사용자 직접 수정은 보존한다.

Git 변경 내역으로 작업 이력을 확인한다. 별도 상태 데이터베이스나 브라우저 편집 기능은 없다. 로컬 내부 공유용이며 고객 메뉴에는 연결하지 않는다. 접근 키·개인정보·내부 비밀정보를 기록하지 않는다. 보드 및 원문 URL은 관리자 로그인 후 이용한다. 운영 공개 전 다중 계정·역할 등 인증 보완과 workboard.md 파일 포함·읽기 권한을 준비해야 한다.
