# 개발·운영 환경 정책 v0.1

결정 기준: D11·D12. 로컬은 Docker 없이 직접 실행하고, 운영은 Docker 기반으로 구성한다. 이 문서는 실행 환경 기준이다. 현재 Next.js·FastAPI 기본 앱과 로컬 설치·실행 스크립트를 구성했으며, 실제 검증 결과는 [개발 기반 검증 기록](reviews/local-development.md)을 따른다. 운영 이미지는 아직 구현하지 않았다.

## 로컬 개발 — 확정

- Windows의 로컬 Node.js에서 Next.js 개발 서버를 실행한다.
- 로컬 Python 가상환경에서 FastAPI 개발 서버를 실행한다.
- Docker Desktop·Docker Engine·Docker Compose 설치나 기동을 요구하지 않는다. 로컬용 Dockerfile·Compose 구성은 만들지 않는다.
- 선택한 DB·캐시·큐·워커 등 필수 서비스도 로컬 직접 설치·실행 경로를 마련한다. 필수 의존 제품은 Windows 지원 또는 실제 사용 가능한 직접 실행 방법을 검증한 뒤 선택한다.
- 외부 PG·메시지·AI는 기본 로컬 개발에서 모의 연동을 사용하고 실서비스 호출을 전제로 하지 않는다.
- 상품 이미지·시안 자산은 로컬 파일 저장 어댑터를 제공하는 방안을 우선 검토한다. 운영 저장소와 권한·메타데이터 계약은 유지한다.
- 로컬 DB와 운영 DB의 핵심 제약·트랜잭션 동작을 일치시킨다. 편의를 위해 서로 다른 DB로 자동 대체하지 않는다.

## 구현 단계 산출물

실제 런타임·패키지 관리 도구·DB 선택 후 버전과 잠금 파일을 기록한다. 프론트·API·필수 서비스의 설치, 환경변수 예제, 초기 데이터, 실행·종료·상태 확인 명령을 마련하고 README에 검증한 명령만 추가한다.

통합 실행 스크립트를 제공할 경우 선행 조건과 포트 충돌을 검사하고, 자신이 시작한 프로세스만 종료한다. 강제 종료나 시스템 서비스 변경을 숨기지 않는다. 로컬 개발 파일·가상환경·의존성·개인 환경변수·DB 데이터는 필요한 범위의 ignore 정책을 마련해 커밋에서 제외한다. 비밀값 없는 환경변수 예제는 버전 관리한다.

## 운영 Docker — 확정 방향

Next.js·FastAPI와 필요한 워커는 운영용 이미지와 실행 구성을 마련한다. 이미지 빌드·기동 검증은 CI 또는 별도 검증 서버에서 수행하며 로컬 Docker 사용을 필수로 만들지 않는다.

운영 기준은 버전 고정·재현 가능한 빌드, 개발 서버 미사용, 비루트 실행, 비밀값 런타임 주입, 헬스체크, 정상 종료, 로그·관측, 영속 데이터의 컨테이너 수명 분리, 마이그레이션·백업·롤백 절차다. 실제 방식은 프레임워크 버전·호스팅 선택 후 검증한다.

운영 DB·저장소를 관리형으로 사용할지 컨테이너로 운영할지, 단일 서버 또는 오케스트레이터를 사용할지는 미정이다. 운영 Docker 방침이 Kubernetes나 Docker Compose 선택을 의미하지 않는다.

## 환경 차이와 완료 조건

개발과 운영의 설정값·비밀·도메인·저장소·외부 연동을 분리하고 API·업무 규칙은 공유한다. CORS·쿠키·프록시·TLS·업로드 경로의 환경 차이를 명시한다.

- 로컬: Docker가 설치되어 있지 않거나 실행되지 않는 환경에서 전체 필수 서비스를 실행하고 웹→API→DB·파일 저장의 대표 흐름을 검증한다.
- 운영: CI/별도 검증 환경에서 이미지 빌드·기동·마이그레이션·헬스체크·정상 종료·배포 복구를 검증한다.
- 두 검증은 서로 대체하지 않는다. 로컬 기본 앱 검증과 운영 이미지 검증을 구분해 기록한다. 운영 이미지 테스트는 아직 수행하지 않았다.


## 로컬 상품 이미지 (WB61)

Pillow 13.0.0을 Python 가상환경에 설치하며 services/api/requirements.txt에 고정한다. 이미지 데이터는 .local/catalog.sqlite3의 별도 테이블에 저장하며 외부 서비스·Docker가 필요하지 않다. schema9 적용 전 SQLite backup으로 파일을 보존한다. 운영 저장소/백업·CDN 설계는 별도이며 로컬 JSON 이미지 조회 방식을 운영 확정으로 간주하지 않는다.


## 공장 계정 로컬 실행 — WB62

추가 Docker/외부인증 서비스 없이 기존 Python·Next 로컬 실행을 사용한다. 내부 관리자가 공장·공급처 등록→상품 담당공장 설정→공장 계정 발급 후 `/factory/login`에서 로그인한다. 운영 분산 세션·초기 비밀번호 강제변경·다중 내부 관리자 개인 계정은 후속 범위다. 로그인 제한은 사용자별5회/15분 및 직접 연결 IP별30회/15분이며 BFF 환경에서 IP제한은 프록시 공통 버킷이다. 운영 trusted-proxy·분산 rate-limit 정책은 미정이다. 자동 이메일/문자 발송은 없다.

## 공장 테스트 계정 — WB82

로컬에서 한 번 다음 명령으로 전용 합성 자료를 준비한다. 기존 업무 자료와 기존 계정은 변경하지 않는다. 비밀번호 출력 없이 .local/factory-test-login.json에 저장하며 해당 파일은 Git 제외 대상이다. 동일 명령을 다시 실행해도 상태를 초기화하지 않는다.

```powershell
.\services\api\.venv\Scripts\python.exe services/api/scripts/seed_factory_demo.py --local-demo --catalog-path .local/catalog.sqlite3 --credentials-path .local/factory-test-login.json
```

Next와 API 실행 후 /factory/login에서 ‘공장 테스트 계정으로 바로 로그인’을 누른다. /admin/login에도 공장 로그인 진입 링크가 있다. 테스트 대상에는 [테스트] 표시가 붙으며 미공유 내부 시안도 준비되어 공유 범위를 확인할 수 있다. 실제 업무 공장 연결을 변경하지 않는다. 운영 빌드에서는 테스트 버튼과 서버 테스트 모드가 비활성이다. seed는 운영 배포/시작 스크립트에서 호출하지 않는다.
